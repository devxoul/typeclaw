The outer typeclaw container is the runtime trust boundary, but model-driven tools do not inherit everything the trusted runtime can access. Runtime code can mediate credentials from `.env`, `secrets.json`, and provider stores; every model-driven bash call runs in a narrower per-tool sandbox, and non-bash tools enforce the same canonical-secret boundary. This matters whenever attacker-controlled content (a PR diff, webpage, or stack trace) steers a model toward hostile tool calls.

The kernel primitive for this is `bwrap(1)` (bubblewrap) — a setuid-less namespace sandboxer that wraps a single subprocess in its own user/pid/mount/net namespace. Per bash call, the wrapper rebuilds an empty rootfs view containing only what the caller's policy declared it needs.

The base layer — the apt package and the `docker run` flag that make bwrap available — is documented below. The reusable command builder that consumes them lives in `src/sandbox/`: an origin-agnostic primitive that takes a bash command plus a `SandboxPolicy` and returns the bwrap-wrapped argv. It knows nothing about subagents or the agent runtime; a consumer resolves a policy from whatever context it has and calls the builder.

## Role-based path hiding

The bash builtin is wired through the builder in `wrapBuiltinToolDefinition` (`src/agent/plugin-tools.ts`) immediately before pi-coding-agent executes it. This wrapper is core runtime enforcement, not something installed by a plugin hook: it runs even when a session has no hook bus. The policy is **not** declared per subagent; it is derived per call from the live turn's resolved role. The sandbox always masks `.env`, `secrets.json`, historical root `auth.json`, `workspace/.config/gws`, the active agent-messenger store at `workspace/.config/agent-messenger`, the legacy masked-only `workspace/.agent-messenger`, and the legacy `.typeclaw/home`, then adds role-dependent private-directory masks. Low-trust roles get a read-only agent root with narrow writable carve-outs. Trusted and owner retain ordinary full-root writes through an RW root bind, but unconditional masks, installed `node_modules` protection, and Git-control protections render afterward. Every mode removes inherited environment names except those the operator declared in `.env` (re-introduced by `inherit`, value in the parent env rather than bwrap argv) and an explicit command-scoped preserve list. `GH_TOKEN`/`GITHUB_TOKEN` are ordinary `.env` vars here — an operator who declares one has chosen to expose it to model bash; on top of that, the `github-cli-auth` broker still injects a narrower per-repo token for validated `gh` calls, and its overlay value wins when both exist for the same name. The trusted runtime's ephemeral `/home/agent` is not bound into bwrap at all, and sandbox `HOME` is rebuilt as `/tmp`; non-bash tools separately deny canonical profiles under `/home/agent`, including the SDK default `~/.config/agent-messenger`. Internal runtime code continues to read credentials through `src/secrets`; model-driven Codex, Claude, GWS, and agent-messenger children never receive reusable auth profiles.

`resolveHiddenPaths` (`src/sandbox/hidden-paths.ts`) maps the resolved role to private-directory visibility. `fs.see.secrets` remains a runtime credential-use capability, not permission for an LLM to read raw credential stores:

| Role           | `fs.see.private` | `fs.see.secrets` | Hidden from bash                                      | Bash writable zones                             |
| -------------- | ---------------- | ---------------- | ----------------------------------------------------- | ----------------------------------------------- |
| guest          | —                | —                | private dirs plus every unconditional credential path | `public/`, `mounts/`                            |
| member         | ✓                | —                | every unconditional credential path                   | `workspace/`, `public/`, `mounts/`, `.git/`     |
| trusted, owner | ✓                | ✓                | every unconditional credential path                   | whole agent root except masked credential paths |

Directories are hidden with `--tmpfs`; single files with `--ro-bind-data`, the only bwrap primitive that masks a file. Each masked file gets its own file descriptor, opened to `/dev/null` by a redirection the builder appends to the rendered command — bwrap closes a `--ro-bind-data` fd once it has copied from it, so sharing one fd across masks aborts the whole invocation with `Can't write data to file <dest>: Bad file descriptor` and takes down every sandboxed bash call, not just the mask. Mount ordering is load-bearing because the last operation on a path wins. For trusted/owner the order is `--ro-bind /agent` → optional command-profile binds under `/tmp` → `--bind /agent` (restore ordinary full-root writes) → canonical masks → read-only existing dependencies and Git controls. For confined roles it is `--ro-bind /agent` → masks → narrow writable-zone binds → the same read-only protections. When `<agentDir>/node_modules` already exists, `resolveProtectedZones` re-binds it read-only for every role; it never creates an absent directory. This protects the installed dependency tree but does not prevent a writable future descendant from acquiring a new `node_modules`. The protected Git set is the real repository's hooks directory, local config (including agent-local include files), Git-parsed effective in-agent `core.hooksPath`, and the `.git` pointer for linked worktrees. Ordinary owner writes and local Git workflows therefore remain available while canonical credential paths resolve to empty overlays and model-driven bash cannot redirect a later privileged Git operation through executable hooks. Every required mask target must be a real entry; symlinks, non-regular files, hardlink aliases, materialization failures, and a target changed during asynchronous policy resolution abort the command. The confined writable set (`src/sandbox/writable-zones.ts`) remains deliberately narrower than the write/edit allowlist and is intersected with role masks.

The agent folder's top-level `public/` directory is the deliberate inverse of this deny-list: it is **never** masked for any role and is in the read-write allowlist, so a guest turn can read and write it through both bash and the file tools. It is scaffolded empty (with a `.gitkeep`) by `typeclaw init`. It sits at the agent-folder root rather than under `workspace/` on purpose — `workspace/` is an arbitrary free-write zone with no reserved subdir names, so a magic `workspace/public/` would silently expose any subdir an agent happened to name `public`. A top-level sibling keeps the deny-list a flat, carve-out-free set (`public/` is simply absent from it) and makes the public/private split legible in the path itself.

The bash masks alone would be hollow: every non-bash tool (`read`, `grep`, `find`, `ls`, `edit`, `write`, plus `find_entry`, `look_at`, and the channel attachment tools) runs in the main process, outside any sandbox. The core tool wrappers therefore apply canonical credential denial unconditionally, without depending on `tool.before`. They also deny `write` and `edit` to the resolved Git config/hooks controls before acknowledgement-based guards run, so owner role or `acknowledgeGuards` cannot bypass this boundary. The bundled security plugin's `privateSurfaceRead` guard (`src/bundled-plugins/security/policies/private-surface-read.ts`) repeats the canonical check as defense in depth and adds the live role's private-directory masks. Both layers also reject `/proc`, `/sys`, `/dev`, and `/run` (including effective symlink aliases) for every non-bash local-file operation; this denial is not acknowledgement-bypassable. The guard realpath-resolves aliases, compares device/inode identity to catch hardlinks, and directs privileged diagnostics to host-side redacted commands (`typeclaw doctor`, `typeclaw provider list`, and `typeclaw channel list`). Direct file consumers execute against private immutable snapshots. `grep`, `find`, and `ls` normalize an omitted root to `.` before security hooks run, then receive bounded descriptor-anchored directory snapshots on Linux and refuse unanchored directory traversal elsewhere. A snapshot whose authorized root resolves exactly to the agent root skips top-level `.git`, `.gitstore`, and `node_modules` before opening them, in addition to canonical credential entries and the live role's hidden subtrees. Visible root discovery therefore remains usable without traversing top-level repository/dependency internals or exposing `.env`, `secrets.json`, `sessions/`, `memory/`, or a guest-hidden `workspace/`. Descendant symlinks are omitted without following them, with non-private omissions reported in the tool result; post-check operand swaps still fail closed. This is a default root-tree omission, not a blanket read denial: an explicitly authorized safe subdirectory or package remains queryable and receives the normal immutable snapshot checks. `secretExfilRead` remains independent defense in depth for credential-like files elsewhere; its acknowledgement and role-bypass semantics are intentionally unchanged.

An ordinary multiply-linked regular input is accepted only when an entry-bounded inode scan accounts for every link outside canonical and role-hidden paths. On Linux the scan opens every traversal root and child with `O_DIRECTORY | O_NOFOLLOW`, then reads and classifies entries through `/proc/self/fd/<fd>` anchors; directory pathname swaps therefore cannot redirect traversal. It pulls entries incrementally, charges each yielded entry to one shared budget before processing it, and closes directory iterators after enumeration while retaining every backing descriptor until the full inventory is complete. Directory identities and parent-identity-plus-name observations are unique within the proof, each entry is re-statted after classification, and every discovered parent directory's identity and mutation metadata must remain stable from discovery through completion of the whole inventory; aliased traversal, repeated observations, entry replacement, same-directory rename churn, or cross-directory moves therefore fail closed instead of inflating the link count. All descriptors close on completion, exhaustion, or error. No directory is first materialized as an unbounded entry array, and symlinks neither contribute an inode identity nor become traversal roots. Denied files and trees are inventoried before visible-link counts can authorize an input. The visible inventory skips top-level `.git`, `.gitstore`, and `node_modules` plus denied roots, and the whole proof fails closed on exhaustion, unreadable entries, or platforms without descriptor anchoring. One inventory and budget are reused across every candidate identity in one guard invocation; the post-budget/open phase builds a fresh inventory for TOCTOU verification. Canonical mask targets, reusable privileged profile mounts, anchored write/edit outputs, and attachment destinations remain single-link.

The guard resolves each candidate to its **real** path before matching — it follows symlinks on every existing path component (walking up to the nearest existing ancestor for not-yet-created targets), and resolves the deny-list entries the same way, because the agent dir itself may sit under a symlink. Lexical resolution alone was a hole: a guest could plant `public/leak -> ../.env` (or `-> ../memory`) via sandboxed bash, then read it back through `read`/`look_at`/a channel attachment whose path lexically lands in the guest-visible `public/`. Real-path resolution closes that.

Which arguments count as paths is **contract-aware**, but unknown plugin and MCP operands remain fail-closed for filesystem-capable values. Plugin tools can declare input, output, exclusive-create, destructive, and non-file operands explicitly. Declared local inputs—including bare filenames—are snapshotted; output/create/destructive operands such as researcher `write_report.path` and memory `delete_topic_shard.path` stay under their dedicated primitives instead of being mistaken for reads. At an unknown generic or MCP boundary, an explicit `file:` URI is automatically treated as an input and pinned regardless of nesting. Existing-local lookup runs before semantic classification, so a real agent entry named like `acme/widgets`, `7/16`, or a package coordinate still requires declaration and pinning. Nonexistent file-shaped keys, canonical credential names, and explicit relative/absolute path forms also fail closed. Narrow key-plus-grammar classifiers suppress only clear false positives: non-file URLs, repository slugs, numeric dates/fractions, safe `/vN/...` API routes, and package coordinates; traversal or malformed lookalikes still reject. Existing entries additionally emit a non-blocking developer diagnostic. Exact first-party operand exemptions, whole-tool no-local-file declarations, and plugin `fileOperands.nonFile` paths remain authoritative. The outer `mcp_call` envelope performs canonical denial but leaves pinning to the dispatcher's inner-args boundary, so an input is pinned exactly once. An MCP server can declare `nonFile` operands over the wire via `_meta['x-file-operands']` on its `tools/list` entries (see [MCP reference](/docs/reference/mcp)); the declaration is surfaced to this pre-execution guard rebased under `args.`, but it only ever waives the generic path-shaped-string heuristic, so canonical credential denial stays unconditional regardless of what a server declares. Outbound attachment `filename` values are display metadata; authorization inspects the declared `attachments[].path`, while fetched-attachment output is sanitized and authorized at its fully resolved anchored destination. Two builtin keys are tool-dependent: `grep.pattern` is a regex, but `grep.glob` and `find.pattern` are path filters and remain subject to the boundary.

Directory operands for `grep`, `find`, and `ls` are copied into immutable snapshots before the tool runs. Only the agent root's immediate `.git`, `.gitstore`, and `node_modules` entries are skipped by default; explicitly requested dependency trees and their regular nested files remain queryable. Recursion never follows symlinks, including package links, dangling links, and links into private surfaces. Private-path links are omitted without revealing their names; other omitted links are reported to the model with a count and up to 12 relative names per input root, so an incomplete search is visible. Non-regular entries such as actual sockets and FIFOs still fail the snapshot loudly rather than being silently dropped; a socket-shaped symlink is handled as a symlink.

Immutable snapshot capacity is process-wide: byte/count leases stay charged until cleanup, queued callers are bounded and abort-aware, source handles are opened only after admission, and streamed growth must acquire capacity immediately or the snapshot fails and is removed. This prevents concurrent calls from each consuming a per-call maximum or accumulating unbounded queued file descriptors.

`look_at` URL inputs use the same safe HTTP policy as `web_fetch`. By default only public HTTP(S) destinations pass; operators can add exact internal hostnames or IPv4/IPv6 CIDRs through the boot-only, model-withheld `TYPECLAW_MODEL_HTTP_*` variables in raw-masked `.env` for intentional private, loopback, link-local, or CGNAT image sources. The fetcher applies the policy to the initial URL and every manually processed redirect. Its `http.request`/`https.request` socket lookup resolves every A/AAAA answer, rejects the whole set if any blocked answer lacks an exception, and returns one validated address to the actual connect without changing the original Host or HTTPS SNI/certificate hostname. Known cloud metadata and control-plane hostnames/IPs are an unconditional floor and never match an exception. The floor recognizes their IPv4 forms in standardized compatible, mapped, translatable, well-known NAT64, and 6to4 IPv6 layouts. It blocks the entire RFC 8215 local-use `64:ff9b:1::/48` range—not because every member maps metadata, but because RFC 8215 permits technology-specific layouts and safe metadata discrimination is impossible without assuming an IPv4 field location. It does not guess arbitrary operator-specific RFC 6052 prefixes or classify unrelated global IPv6 by its low 32 bits. Every redirect repeats that socket-bound lookup. Redirect count, concurrency, timeout, streaming bytes, and aggregate bytes remain capped; local paths and base64 images share the same aggregate image budget.

Write/edit destination anchoring and channel attachment saves use Linux directory/file descriptors through `/proc/self/fd`, reject symlink components and multiply-linked targets, and authorize the intended destination before truncation. Output authorization opens the existing parent and either opens an existing single-link regular target with `O_NOFOLLOW` or atomically reserves a missing target with `O_CREAT | O_EXCL | O_NOFOLLOW` and normal `0666`-before-umask file mode. It holds that file descriptor through dispatch and rewrites the tool argument to `/proc/self/fd/<fd>`, so later basename replacement cannot redirect the write; cleanup verifies that the parent entry still names the same single-link inode before closing both file and parent descriptors. An exclusive `create` operand instead verifies absence, holds the parent descriptor, and passes `/proc/self/fd/<parent-fd>/<basename>` to the plugin's own `O_CREAT | O_EXCL` primitive; cleanup requires the created entry to be a single-link regular file under that same parent. Authorization does not create missing parent directories. Missing parents are created one component at a time only by the attachment writer; generic write/edit paths require an existing anchored parent. These model-driven output operations fail closed outside Linux rather than silently falling back to a lexical pathname. TypeClaw's runtime container is Linux; host-side dev invocations on other platforms should exercise these operations in the container.

The enforcement layers are intentionally independent. Bash masking and canonical non-bash denial live in the core wrappers and remain active in a hookless session. The bundled `security` plugin contributes role-private non-bash denial and repeats the canonical scan as defense in depth. A missing or broken hook bus can therefore reduce role-specific policy coverage, but it cannot expose canonical credentials or turn bash into an unsandboxed fallback. `channel_send` / `channel_reply` reading a role's _hidden_ directory is blocked by the plugin layer, while canonical credentials are blocked by both. The broader "a role that legitimately sees `workspace/` forwards it to a public channel" remains the authn-shaped output-exfil concern this sandbox does not solve — use separate agents per trust domain.

This hiding is filesystem read/exec only. A guest turn is still recorded to memory normally — guest simply cannot read the private surface back through bash or the file tools.

## Custom writable paths and symlinks

The built-in writable set covers the common scratch zones, but some CLIs insist on writing a fixed config dir under the agent root — e.g. a tool that rewrites `<agentDir>/.foo-cli/config.json` on every run. Under a low-trust role that dir is `EROFS`, and there was previously no supported way to allow it. Two `sandbox` config fields close that, both `restart-required` (read from the boot-time `config` snapshot, like `realProc`).

**`sandbox.writablePaths`** is an array of agent-root-relative directories added to the writable set on top of the built-ins:

```json
{ "sandbox": { "writablePaths": [".foo-cli", "workspace/cache"] } }
```

Entries are validated at two layers. At **parse time** (`relativeAgentPathSchema`): relative-only (absolute container paths rejected), no `..` segments, no null bytes. At **resolve time** (`resolveWritableZones`, `src/sandbox/writable-zones.ts`) entries are _dropped_ — never thrown, so a stale config degrades one path instead of aborting sandboxing — unless they exist, are a real directory (not a file), have a non-symlink root, resolve inside `agentDir` (and are not the agent root itself), and do not land on a security-sensitive root. Canonical credential roots come directly from `src/sandbox/canonical-secrets.ts`; `.git`, `sessions`, `memory`, `.typeclaw`, and `node_modules` add broader system boundaries. Configured paths still pass through `subtractMasked`, so a role's hidden paths are never re-exposed read-write.

**`sandbox.symlinks`** is the one-entry abstraction for the CLI case above: it creates the symlink **and** makes its target writable.

```json
{ "sandbox": { "symlinks": [{ "from": "~/.foo-cli", "to": "workspace/.foo-cli" }] } }
```

`from` is the symlink **location** and is fully configurable — an absolute container path (`/root/.foo-cli`) or a `~/`-prefixed path. `to` is agent-root-relative (reuses `relativeAgentPathSchema`) and is automatically folded into the writable set (`getSandboxWritablePathSpecs`), so the operator never lists it twice. `from` validation rejects null bytes, the filesystem root `/`, any path under `/agent` (a self-referential loop), and the kernel/virtual roots `/proc`, `/sys`, `/dev`, `/run`; `/etc/...` is allowed because the entrypoint's no-clobber guard already prevents overwriting an existing system file.

Model-driven bash always runs with bwrap `HOME=/tmp` (the per-session tmp bind). `applyBashSandbox` emits configured links inside that HOME after the `/tmp` bind. Confined roles only receive links whose targets survived as writable directories; full-root trusted/owner roles retain every validated configured link. The entrypoint's `/home/agent` links remain available to runtime-owned processes outside model tool execution.

**Privileged CLI compatibility.** `resolvePrivilegedSandboxRuntime` never mounts Codex, Claude, GWS, or agent-messenger auth into a model-driven child: each CLI can read or upload arbitrary files, so command-shape parsing cannot make reusable refresh credentials safe. Agent-messenger's active per-agent store is `workspace/.config/agent-messenger`; `workspace/.agent-messenger` remains masked only for interrupted migrations and older installs. Those CLIs still run with no preserved credential environment and empty temporary config, preserving version/help and honest unauthenticated diagnostics. A standalone local Git command may receive a generated `/tmp/.gitconfig` containing only `user.name` and `user.email`; includes, credential helpers, HTTP headers, signing commands, aliases, and every other source field are dropped. The generated mount is revalidated by file type, link count, device, and inode immediately before rendering, and its temporary directory is removed after the tool call on both success and failure. On fresh container creation, TypeClaw also resolves a complete `user.name`/`user.email` pair already configured in the agent repository's effective local config and injects it as the four standard Git author/committer variables. Model bash inherits only those identity variables, so commits in newly cloned `/tmp` repositories retain the agent repository identity while `GIT_CONFIG*`, global config, and system config remain unavailable. The runtime variables take precedence over same-named `.env` values and the generated sanitized config. A changed host identity takes effect after `typeclaw restart`, which recreates the container.

GitHub credentials use a separate command-scoped overlay only after an allow-known-good argv classifier accepts the direct `gh` operation. Gist creation, release upload, `gh api --input`, file flags, host selection, gh-owned jq/template rendering, aliases, extensions, and compound commands are rejected before injection. Inline raw fields (`-f`/`--raw-field`) and typed fields (`-F`/`--field`) are allowed only as safe `key=value` arguments whose value does not begin with `@`; typed scalar values such as `-F number=7` therefore work, while every `@file` dereference is denied. The token value is inherited by name from the trusted parent environment and never appears in the bwrap command line. A trailing reader pipeline is separately allowlisted and every downstream process is launched through `/usr/bin/env -u GH_TOKEN -u GITHUB_TOKEN`. `grep` is permitted only with known stdin-shaping flags and either one positional pattern or one-or-more `-e`/`--regexp` patterns, never file operands; its stage also unsets `GREP_OPTIONS` and pins `/usr/bin/grep` so environment or PATH configuration cannot add an input source after validation. Authenticated Git does not reuse the direct-`gh` overlay: eligible configured-remote pushes receive a repository-bound `GIT_ASKPASS` overlay for App/PAT credentials, while trusted-store fallback runs against a clean runtime-owned Git directory and transport. This is a confidentiality guarantee, not merely a shell-shape heuristic: no accepted child argument can ask `gh` or a downstream reader to read `/proc/self/environ`, a sibling process environment, or another file and disclose the credential.

**Per-session `/tmp`.** `applyBashSandbox` binds a per-session scratch dir (`/tmp/typeclaw-session/<sessionId>`, created `0700` by `src/sandbox/session-tmp.ts`) over `/tmp` for every role. The path-based file tools run in the main process, so the wrapper redirects their model-facing `/tmp/*` paths to the same backing dir and reverses that path in receipts. Bash calls within one session therefore share normal Unix scratch state without seeing the container's real `/tmp` root or an unrelated session's scratch. A subagent tree is the exception by design: `enterSubagentTmpScope` (registered by `createSessionWithDispose` once creation succeeds, released on dispose) resolves every descendant of a top-level subagent to that subagent's scratch dir, so a `/tmp` path handed down the tree — a reviewer checkout receipt passed to its explorers — resolves in each of them. The scope is anchored below the spawning channel/TUI/cron session, never at it: that session persists across turns and speakers, so subagent artifacts never land in its scratch, and sibling top-level subagents stay isolated from each other. Parallel descendants of one subagent can collide on fixed scratch filenames, exactly as parallel tool calls within one session already can; use unique names (`mktemp`) for concurrent scratch. A trusted deferred bash preparation may append a narrower runtime-owned `ro-bind` after this broad writable bind. The gh-store fallback uses that contract for its clean bare Git directory: it is created outside session scratch only after loop/final/subagent gates pass, overlaid read-only at a unique `/tmp` destination by last-op-wins ordering, and owned by `PreparedBashSandbox.cleanup` across success, build failure, execution failure, and remediation retry.

**Runtime-owned Git is hookless.** TypeClaw's deterministic Git operations (initialization, system-file commits, backup commit/push/rebase, doctor auto-fix commits, ignored-file reconciliation, and memory snapshots) prepend `-c core.hooksPath=/dev/null` through one shared argument helper. This is deliberately stronger than `--no-verify`: it covers every hook-capable Git subcommand and prevents an operator- or model-planted hook from inheriting runtime credentials or network authority. Model-requested Git keeps normal Git semantics inside the sandbox; only TypeClaw-owned operations disable hooks.

**Live role on the turn.** For channel origins the cached system-prompt role block is a multi-speaker _policy_ — it does not assert a concrete role or leak the opener's permission list, because a channel session is keyed by chat/thread and sees many speakers. The router re-resolves the role per turn for tool gating and surfaces it to the model as a `<your-role authority="current-speaker">…</your-role>` tag injected into the user turn (omitted for `owner`, the unconstrained default). The tag is marked authoritative and explicitly overrides the cached block, so an owner-opened session does not make a later guest speaker look like an owner. This is cache-free — the tag lives in the non-cacheable user-turn suffix, never the cached system-prompt prefix. The agent uses it to route output: shareable artifacts for an untrusted caller go to `public/`, and a `denied by permissions` block on a `workspace/` write is the runtime fallback signal that the caller is untrusted.

**`system` origin for runtime infrastructure.** Memory logging (`memory-logger`), backup, and dreaming are TypeClaw-owned infrastructure that operate on the operator's own state, not user-delegated work. They spawn under a `system` session origin that resolves to `owner`, so a guest channel turn that _triggers_ memory logging does not demote the logger to guest and get its own `sessions/`/`memory/` access blocked by `privateSurfaceRead`. The triggering origin is preserved as `triggeredBy` for honest audit provenance (never a synthetic-TUI lie) and dropped from the persisted projection so channel author identity does not reach git-backed `sessions/`. The `system` kind is constructed only by runtime/bundled code — inbound channel/cron _content_ can never produce it — so resolving it to `owner` is not a role-laundering vector. Role is authorization, not observability: guest turns remain eligible for memory logging; the confidentiality boundary lives at retrieval/output, not at logging.

**Symlink handling.** For **bash**, a symlink whose target lives _under_ `/agent` (e.g. `public/link -> /agent/.env`) resolves inside the sandbox mount namespace to the masked overlay, so it cannot reach the real secret. For the **non-bash file tools** there is no mount overlay, so the core canonical check and plugin `privateSurfaceRead` guard do the real-path resolution described above. Direct file consumers additionally use the verified immutable-copy handoff, closing the check/open race if an alias changes concurrently. A symlink pointing _outside_ `/agent` escapes the agent-folder bind entirely and is not covered by agent-path masks; it is still subject to the tool's normal path policy and the bash kernel-containment invariants below.

**Wiring invariant.** Every session construction supplies the builtin-tool wrapper with either the live permission service or the deny-all service. `wrapBuiltinToolDefinition` independently rejects any bash call whose wrapper omitted the service, and rejects an empty canonical dir/file mask set. There is no no-permission unsandboxed fallback, including in bare harnesses. The same core wrappers unconditionally enforce non-bash canonical denial from `src/sandbox/canonical-secrets.ts`; the bundled security plugin repeats that check and adds role-private paths.

## What the per-tool sandbox is NOT for

This sandbox limits what a single prompt-injected `bash` call can do **within one agent's trust domain** — hide secret-shaped reads, contain the network, mask the private surface. It is defense in depth against a hostile command, not a wall between trust domains.

Trust-domain problems come in two shapes, and they need different defenses. The sandbox addresses neither directly; naming both keeps "just sandbox it" from being mistaken for a complete answer.

| Shape                                       | Threat                                                                                                                                                                                      | What it wants                                                                     | The defense                                                                      |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| **Authentication-shaped** (confidentiality) | "Hide the private thing from the attacker." A public-facing review and a private repo share one agent; a public PR steers bash and reaches `.env` / `GH_TOKEN` / `/agent` / private source. | A coarse, whole-container / whole-credential boundary.                            | **Separate agents per trust domain.**                                            |
| **Authorization-shaped** (action gating)    | "We can both _see_ the repo and both _propose_ changes, but only I may _act_ — merge, push to `main`." Nothing is secret; the question is purely who may perform the privileged action.     | Fine, per-action authority that reflects the least-privileged actor in the chain. | **Provenance + action gating** — see [Permissions](/docs/internals/permissions). |

### Authentication-shaped: separate agents

Keeping a public-facing review away from private code and credentials is coarse — it wants a whole-container, whole-credential-set boundary — and typeclaw already provides it: one agent is one container, one `.env`, one `GH_TOKEN`, one `/agent`. The right boundary is operational.

**Use separate agents for separate trust domains.** Do not point one agent at both a private repo and public-facing review work (e.g. reviewing external contributors' pull requests). If a public PR can steer the agent's bash, the only things it can reach are that agent's own container and credentials — so that container must not also hold the private repo or its secrets. Splitting the work across agents makes the public-to-private pivot impossible by construction, and closes the subtler residual the sandbox cannot: a prompt-injected reviewer copying private source into review text that then gets posted to the public PR. With public and private in separate agents, that output channel has nothing private to leak. The role-based path hiding above is a within-domain mitigation, not a substitute for this split.

**`public/` is a confused-deputy egress sink, by the same logic.** The path hiding stops a guest from _reading_ the private surface, but a higher-role turn in the same channel session shares one model context. A guest who prompt-injects an owner/trusted-role turn into copying `workspace/secret` → `public/` (which the guest can then read) has exfiltrated it — the write is a legitimate, authorized action, and `public/` exists precisely to be guest-readable. This is the authentication-shaped problem again: the defense is the same trust-domain split, plus not treating `public/` as a dumping ground for content derived from the private surface. Outbound secret scanning covers `channel_send`/`channel_reply` text but not file writes, so it does not catch this. Treat `public/` as published-to-the-least-trusted-reader, and keep genuinely private work in a separate agent.

### Authorization-shaped: separation does not help

This shape survives separation, because the resource is **not** secret — the public repo _is_ the work, visible to attacker and operator alike. Sandboxing misses it too: `gh pr merge` is a legitimate, authorized API call, not a containment breach. The boundary is purely _who may act_.

This is the `operator` subagent's surface. Subagent provenance stamps `spawnedByRole` — the role of whoever _spawned_ the subagent (see [Permissions](/docs/internals/permissions)). It tracks who spawned the task, not whose _content_ is driving it. So an owner-spawned operator resolves to `owner`; if an owner (or owner-scheduled cron) hands it "act on PR #N" and the attacker-controlled diff carries a prompt injection ("merge this / push to `main`"), the action runs with the owner's authority. The defense is the same principle the cron/subagent provenance guard establishes: provenance should reflect the least-privileged actor in the chain, and irreversible or audience-visible actions should be action-gated regardless of inherited role.

## bwrap is a primitive, not a policy

Upstream bubblewrap is explicit: "bubblewrap is not a complete, ready-made sandbox with a specific security policy" and "the level of protection... is entirely determined by the arguments passed to bubblewrap." Treating "we use bwrap" as a security claim is a category error. The boundary lives in the **builder invariants** — the exact bwrap argv `src/sandbox/build.ts` constructs per call. The always-on invariants are:

- `--unshare-all` — covers the user/pid/mount/net/ipc/uts/cgroup namespaces.
- `--clearenv` followed by an explicit `--setenv` allowlist (`PATH`, `HOME`, `LANG`, `BUN_TMPDIR`, `BUN_INSTALL`). On top of that, the vars an operator **declared in `.env`** are re-introduced by `inherit` (value stays in the parent env, out of the bwrap argv) — `.env` is the operator's deliberate expose-to-the-agent surface, so everything they put there reaches model bash by design. Credentials that must stay hidden from the agent belong in `secrets.json`, which is never inherited into bash. This includes `GH_TOKEN`/`GITHUB_TOKEN`: a GitHub token declared in `.env` reaches model bash like any other operator var (so plain `gh`/`git`/`curl` work in agents with no GitHub channel), while the `github-cli-auth` broker separately injects a narrower per-repo token for validated `gh` calls. A few classes are withheld, and none is about credential-hiding by name — they protect the sandbox **mechanism** and the runtime's host-injected tokens: the sandbox-owned names (`PATH`/`HOME`/`BUN_*`/`LANG`, which a `.env` value would otherwise override); process- and shell-hijack vars that execute in the outer `bash -c` before bwrap or change how the loader runs (`LD_PRELOAD`, `NODE_OPTIONS`, `BASH_ENV`, `SHELLOPTS`, `BASHOPTS`, `PS4`, `BASH_XTRACEFD`, the `BASH_FUNC_` prefix, `GIT_CONFIG_*`, `SSH_AUTH_SOCK`, `KUBECONFIG`, …); and the host/container-injected runtime tokens `TYPECLAW_TUI_TOKEN`/`TYPECLAW_HOSTD_TOKEN`/`TYPECLAW_HOSTD_BROKER_TOKEN` (never something an operator writes in `.env`). Except for the four runtime-resolved Git identity variables (`GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`), eligibility is decided from the **parsed `.env` file value** (a non-empty declaration), not `process.env`: an empty line like `DISCORD_BOT_TOKEN=` is not an expose-choice even if `hydrateChannelEnvFromSecrets` later populates `process.env` from `secrets.json`. The Git identity exception exposes only those four exact names when their runtime values are non-empty; `GIT_CONFIG_*` and every other process-only variable remain withheld. The bwrap parent env is an exact snapshot taken at policy-build time so a secret added between build and spawn cannot be inherited. See `src/sandbox/env-exposure.ts`.
- `--new-session` plus `--die-with-parent` (both default-on) to prevent the contained process from injecting input into the controlling terminal via TIOCSTI and to tear the sandbox down if the agent dies. `--die-with-parent` installs `PR_SET_PDEATHSIG(SIGKILL)`, so it _terminates_ the sandbox; it does not _reap_ the corpse, because reaping requires a parent that waits and the signalled process has already been orphaned. `--new-session` calls `setsid()`, which moves the sandbox out of the process group an outer `kill(-pid)` targets, but shields it from neither the parent-death SIGKILL nor the kernel rule that killing a pid namespace's PID 1 kills every process in it. Collecting the resulting orphan is the container init's job — see [`--init`](#--init-and-the-namespace-ucount-leak).
- A minimal mount set (`--ro-bind /usr`, `--ro-bind /etc`, `--dev /dev`, `--tmpfs /tmp`, plus a `/proc` per the resolved strategy — default `--ro-bind /proc /proc` under `proc-bind`, see the `/proc` section). Every additional bind-mount a policy declares is a potential write/exec/read vector; everything mounted in can "potentially be used to escalate privileges" (bubblewrap docs).
- The usr-merge root symlinks (`--ro-bind-try /bin`, `/sbin`, `/lib`, `/lib64`). On the Debian base these are root-level symlinks into `/usr`, so `--ro-bind /usr` exposes `/usr/bin` etc. but **not** the root entries themselves. Anything the kernel resolves by absolute path _without_ consulting `PATH` then breaks: the ELF interpreter baked into a binary's `PT_INTERP` (`/lib/ld-linux-aarch64.so.1` on arm64, `/lib64/ld-linux-x86-64.so.2` on amd64 — its absence surfaces as the misleading `bwrap: execvp bash: No such file or directory`, where the missing file is the loader, not bash), and `#!/bin/sh` / `#!/bin/bash` shebang lines (literal paths that skip `PATH`, so a script fails `cannot execute: required file not found` even though `/usr/bin/sh` exists). `--ro-bind-try`, not `--ro-bind`: the set is arch- and base-dependent (the arm64 `oven/bun` slim base ships `/lib` but no `/lib64`), and a hard bind of an absent source aborts bwrap; `-try` binds each only when present, keeping `build.ts` pure (no host filesystem probe). These are the loaders and interpreters the sandboxed workload needs; they are not a widening of the read surface beyond what `/usr` already exposes.
- Network isolation by default (`--unshare-all` leaves the net namespace unshared); `--share-net` only when a policy explicitly sets `network: 'inherit'`.

These invariants are the always-on **kernel containment** boundary, applied to every command regardless of policy. Command-syntax restrictions — a prefix allowlist or shell-metacharacter rejection — are _optional_ `commandFilter` knobs a narrow consumer (e.g. a read-only reviewer) can opt into; they are not part of the base boundary, because a general-purpose bash sandbox must allow pipes, `&&`, and `$()`. Reviewers of any consumer should audit the resolved policy and the argv construction, not just confirm that `bwrap` was invoked.

## Container security options: seccomp and AppArmor

`planStart()` in `src/container/start.ts` adds `--security-opt seccomp=unconfined` and `--security-opt apparmor=<sandbox.apparmorProfile>` before the image tag. The AppArmor profile defaults to `unconfined`. Without the seccomp option, Docker's default seccomp profile blocks `unshare(CLONE_NEWUSER)` and `clone(CLONE_NEWUSER)`. Without the AppArmor option, moby's `docker-default` profile applies an explicit `deny mount,` rule, and bwrap's opening `mount(NULL, "/", MS_SLAVE|MS_REC)` fails with `Permission denied` before even `echo` can run.

`apparmor=unconfined` is a profile selection, **not** a capability grant. It is a strict improvement over docker-default, and it is sufficient on Debian, pre-23.10 Ubuntu, and hosts where `kernel.apparmor_restrict_unprivileged_userns=0`. Stock Ubuntu 23.10+ defaults that sysctl to `1`; its `unprivileged_userns` catch-all then denies `proc/<pid>/uid_map` writes for an unconfined non-root process, producing `bwrap: setting up uid map: Permission denied`. Adding `SYS_ADMIN` cannot bypass this: the entrypoint drops to the host UID with `setpriv --reuid ... --bounding-set=-all --inh-caps=-all --ambient-caps=-all`, so the production agent is non-root with an empty capability set and Docker's `--cap-add` contributes nothing.

### Ubuntu 23.10+ operator setup

TypeClaw ships the narrowly-scoped host profile at `scripts/apparmor/typeclaw-bwrap`. From an initialized agent folder, install and load it on the host, select it in `typeclaw.json`, then recreate the container:

```sh
sudo install -m 0644 ./node_modules/typeclaw/scripts/apparmor/typeclaw-bwrap /etc/apparmor.d/typeclaw-bwrap
sudo apparmor_parser -r -W /etc/apparmor.d/typeclaw-bwrap
```

```json
{ "sandbox": { "apparmorProfile": "typeclaw-bwrap" } }
```

```sh
typeclaw restart
```

`typeclaw doctor` detects the affected host-policy/config combination and prints this recovery path. It reports `docker-default` — and `unconfined` on a restricted host — as an **error**, because an unavailable sandbox makes every model bash call throw `SandboxUnavailableError`; the surface is dead, not degraded. A profile it does not ship is reported as unverified rather than working. Loading a host profile requires root and deliberately remains an operator action outside the blocked model-bash surface.

The shipped profile grants more than `userns` and `mount`. Under the pinned `abi <abi/4.0>`, AF_UNIX and signals are separately mediated classes, so the profile names them explicitly:

- `unix,` — Xvfb's `/tmp/.X11-unix` socket and the runtime's local IPC. Not covered by `network,`.
- `signal (send,receive) peer=typeclaw-bwrap` — the runtime cancelling its own sandboxed bash on timeout or abort. Every process in the container carries the container profile, bwrap children included, so a cancellation kill is a same-profile send.
- `signal (receive) peer=unconfined`, `peer=runc`, `peer=crun`, `peer=snap.docker.dockerd` — `docker stop`/`docker restart`, whose SIGTERM originates outside the profile. `peer=unconfined` alone is not enough: Ubuntu 23.10+ confines the OCI runtime, and `docker stop` commonly reaches PID 1 through `runc kill` rather than the daemon. A peer profile that is not loaded on a given host is inert, not an error; an operator running a differently labelled daemon must add that label locally.

Both failure modes are quiet. A denied cancellation leaves a runaway sandbox; a denied SIGTERM turns every `typeclaw stop` into a full wait for dockerd's SIGKILL. Neither surfaces as a bwrap error, which is why `scripts/verify-apparmor-signals.sh` is a separate release gate from the mask lane — the mask lane's sandboxed command exits naturally and therefore never crosses the profile with a signal at all.

The default Docker profiles are calibrated for multi-tenant hosts. TypeClaw's outer container is single-tenant: the user owns the host, the agent folder is bind-mounted in, and runtime secrets already enter the container. Selecting permissive seccomp/AppArmor profiles drops outer AppArmor's mandatory-access-control restrictions over operations such as mount and ptrace and access to `/proc` and `/sys`. It does **not** remove Docker namespaces, the capability bounding set, cgroups, device restrictions, masked paths, or the inner per-call bwrap boundary. That inner boundary remains the load-bearing containment against prompt-injected commands. Replacing the outer defaults with tighter compatible profiles is valid; silently restoring docker-default is not, because it disables the authorized bash workflow wholesale.

## `--memory` and the swap livelock

`planStart()` also adds `--memory` and `--memory-swap` set to the **same** value. The equality is the load-bearing half: it disables swap for the container.

Without a cgroup limit, growth inside one container is charged straight to the Docker VM. The guest kernel answers the pressure by writing to swap, every vCPU ends up in direct reclaim (`shrink_folio_list` → `swap_writeout`), and the OOM killer frees nothing reclaimable — much of the footprint is `/dev/shm` tmpfs, which a process kill cannot reclaim at all. The VM livelocks on `VM_FAULT_OOM leaked out to the #PF handler` instead of killing one process, and every container on the host dies with it. With the limit, the charge fails at the cgroup boundary and a single agent is killed with a legible cause. A limit also makes `/dev/shm` pages count against the container rather than the host.

The value is a fixed 6 GiB, sized to hold the Bun runtime, the embedder during an index build, a headless Chrome on a heavy page, and whatever of the 2 GiB `/dev/shm` allowance Chrome touches. It is clamped **down** when the Docker VM cannot spare it (2 GiB of VM headroom, 1 GiB floor) and never scales **up** with a larger machine — a fraction-of-RAM rule would oversubscribe by the agent count on a shared host, and an ambient-dependent budget makes incidents unreproducible. The clamp reads the Docker daemon's own memory total, not the workstation's, which on macOS, Windows, and remote-daemon setups is a different number.

There is no config knob. The failure this prevents needed a ceiling, not an option, and `typeclaw start` warns when the limits of all running agents together oversubscribe Docker's memory.

`--memory` is create-time `HostConfig` state, so like `--init` it takes effect on the next container create — `typeclaw restart`, not `docker restart`.

## `--init` and the namespace-ucount leak

`planStart()` also adds `--init` unconditionally. Docker puts its bundled `docker-init` (tini) at PID 1 and demotes the entrypoint shim to PID 2. This is a correctness requirement of the per-tool sandbox, not container hygiene.

Every model bash call runs the sandbox under `bash -c`, and every call mints a fresh user namespace — on **both** proc strategies, not just the default. Under `proc-bind`/`tmpfs` that is `bwrap --unshare-all` (user **and** pid together); under `sandbox.realProc` the pid namespace is split out into `unshare --pid --fork --mount --mount-proc` and bwrap takes the user namespace via an explicit `--unshare-user`. Either way the per-call user namespace is charged, so the leak below is not specific to the default strategy.

On timeout or abort the upstream bash tool SIGKILLs the process _group_ (`process.kill(-pid, 'SIGKILL')` in pi's `killProcessTree`). SIGKILL only _terminates_ — the reaping happens separately, because the tool holds a child handle for the `bash` it spawned and waits on it. The sandbox process one level down is not a process it holds a handle for, so it is re-parented to PID 1 instead. Before `--init`, the entrypoint shim `exec`ed into bun, so PID 1 was the Bun runtime — and a JS runtime never `wait()`s on orphans it did not spawn. That descendant therefore stayed a zombie for the life of the container.

A zombie is not free. It drops its `nsproxy` at `do_exit()`, so the mount and net namespaces are released early, but it keeps its `struct cred` until it is reaped, and `cred->user_ns` pins the user namespace; its surviving `struct pid` pins the pid namespace, which references that same user namespace again. `exit_creds()` only runs on the final `task_struct` release, which reaping drives — so an unreaped orphan pins its user namespace forever, and the `UCOUNT_USER_NAMESPACES` charge is only returned by `free_user_ns()`.

That charge is accounted against the **ancestor** user namespace. The resource that runs out is therefore the _host_ kernel's `user.max_user_namespaces`, shared across every container on the box — which is why the container's own `max_user_namespaces` reads as effectively unlimited while `bwrap` still dies with `unshare user ns: No space left on device`, and why one leaking agent can take down every other typeclaw container on the same host. Raising the host sysctl only defers the exhaustion; reaping is the fix.

`--init` was chosen over baking `tini` into the image because the per-agent Dockerfile pins a published, version-locked `typeclaw-base:X.Y.Z` — a new baseline apt package would not exist in already-released base tags. The flag needs no image change and takes effect on the next container create.

`--init` is create-time state. A container launched before the flag existed keeps leaking, and `start()` deliberately no-ops on a live container. Recovering a running deployment requires `typeclaw restart` (stop, archive, remove, recreate); a plain `docker restart` frees the currently-leaked namespaces but reuses the old `HostConfig`, so the leak resumes immediately.

## `--cap-add=SYS_ADMIN` and `sandbox.realProc`

`CAP_SYS_ADMIN` looks narrower than permissive seccomp/AppArmor profile selection, but would be broader in practice if retained: it is called "the new root" because it controls `mount`, `swapon`, `sethostname`, namespace operations, `bpf`, `perf_event_open`, and more. It is also not an AppArmor workaround here. The production entrypoint changes to a non-root UID and clears every bounding, inheritable, and ambient capability, so a Docker `--cap-add=SYS_ADMIN` does not reach the running agent at all. AppArmor profile selection authorizes the namespace setup operation without pretending a capability grant survives that handoff.

Running ephemeral external package CLIs (`bunx` and `bun run <pkg-bin>`) inside the sandbox is a hard requirement — the bundled agent-messenger skills shell out to `bunx agent-*`, and under the bare `--tmpfs /proc` profile every such call aborts with Bun's `error: An internal error occurred (NotDir)` (see the OrbStack `/proc` section below). This stack does **not** claim descendant-proof persistent package-install isolation: a writable tree can gain a newly created descendant and install its own `node_modules`, so lexical command classifiers and pre-enumerated path fences are not authorization boundaries. A future compatible guarantee requires a runtime-owned read-only package broker. The `/proc` fix does **not** need `CAP_SYS_ADMIN`: the default `proc-bind` strategy `--ro-bind`s the container's already-real procfs into the sandbox, giving an allowed runner's child a working `/proc/self/{fd,maps}` with no mount and no capability. So `typeclaw.json#sandbox.realProc` **defaults to `false`** and `planStart()` does **not** add `--cap-add=SYS_ADMIN` by default.

`sandbox.realProc: true` remains the sole path that asks Docker for `--cap-add=SYS_ADMIN`, because mounting a fresh procfs in a new PID namespace requires it. Under the current non-root entrypoint that requested cap is cleared before the agent starts, so the container-side capability probe rejects `real-proc` and falls back to `proc-bind`. The request is off by default, and `proc-bind` already supports the core external-package workflow without either the capability or full PID isolation.

## Why not a custom seccomp profile

A seccomp profile based on Docker's default plus the namespace/setup syscalls in the exact bwrap invocation would be narrower than `seccomp=unconfined`. The full syscall delta includes `mount`, `pivot_root`, and related namespace setup and varies with the selected `/proc` strategy and architecture. It would need to be traced against every supported rendered argv and kept synchronized with the unpinned bwrap package.

The reason we do not ship a custom **seccomp** profile today is maintenance: its syscall allowlist would have to track bwrap and every supported architecture. This is distinct from the shipped **AppArmor** profile, which is required on stock Ubuntu to grant the coarse `userns` and mount operations that host policy otherwise denies. Single-tenant deployments keep `seccomp=unconfined`; Ubuntu operators load the AppArmor profile rather than relaxing a host-global sysctl.

## bwrap in baseline

`BASELINE_APT_PACKAGES` in `src/init/dockerfile.ts` includes `bubblewrap` (~132KB). Per-tool sandboxing is a runtime concern decided by the agent, not by the agent author, so it ships unconditionally rather than behind a `docker.file.bwrap` toggle. The package and security-option pair (`seccomp=unconfined` plus the configured AppArmor profile) are load-bearing together. On restricted Ubuntu, the host-loaded shipped profile is a fourth required piece. Dropping any one breaks the sandbox with no signal until bwrap executes; the release production lane exercises this exact Ubuntu path. Both release verifier lanes run the payload as a non-root UID with every capability mask empty and assert that posture before invoking bwrap, because the published base image carries no `ENTRYPOINT` and so never replays the `setpriv` handoff that gives production its actual privilege shape.

## OrbStack `/proc` quirk

OrbStack's hardened VM kernel blocks `mount("proc", ...)` from user namespaces regardless of caps. Bare-metal Linux and Docker Desktop allow it; OrbStack does not. This is why the `real-proc` strategy (which `unshare --mount-proc`s a fresh procfs) cannot be the default — on the most common host it is rejected outright. The default `proc-bind` strategy below sidesteps the mount entirely: it `--ro-bind`s the container's already-real procfs, which needs no `mount(2)` and works on every host.

The historically-rejected alternative was `--tmpfs /proc`: the sandbox gets an empty `/proc`, which breaks `ps`/`top`/`/proc/cpuinfo` readers, bash process substitution `<(…)` / `/dev/fd/N`, and — most importantly — **the child process a JS package runner spawns**, which reads `/proc/self/fd/N` and `/proc/self/maps`. That last case is why a `--tmpfs /proc` sandboxed `bunx <pkg>` / `bun run <pkg-bin>` aborts with Bun's `error: An internal error occurred (NotDir)`: the runner's own self-location can be patched with a `/proc/self/exe` symlink, but the spawned bin's `/proc/self/fd` lookup still hits the empty tmpfs. So `--tmpfs /proc` survives only as a last-resort fallback (no external package execution); it is **not** a default.

### `sandbox` default: `proc-bind` — real `/proc` without the leak, without the cap

The default per-tool strategy. It binds the container's already-real procfs straight into the sandbox:

```
bwrap --unshare-all … --ro-bind /proc /proc … bash -c <command>
```

`--ro-bind /proc /proc` gives the runner's child a real `/proc/self/{fd,maps,exe}`, so allowed `bunx`/`bun run <pkg-bin>` calls stop aborting with `NotDir`. No `unshare --mount-proc`, no `CAP_SYS_ADMIN` — which is exactly why it works on OrbStack where `real-proc` is rejected.

It does **not** leak the agent runtime's `/proc/<agent>/environ` (`OPENAI_API_KEY`, `GH_TOKEN`). `--unshare-all` puts the sandboxed bash in a **child user namespace**, mapped-root rather than real-root. The kernel's `PTRACE_MODE_READ_FSCREDS` check on `/proc/<pid>/environ` requires the reader's userns to be the target's userns or an ancestor of it; a child userns is neither, so the read fails with `EACCES`. The same userns boundary blocks `kill()`/`ptrace` against those pids (`EPERM`, no `CAP_KILL` in the parent userns). The residual is non-secret metadata: other pids' `cmdline`/`status`/`stat` stay visible, because `proc-bind` (unlike `real-proc`) does not put the sandbox in a fresh PID namespace. On the single-tenant boundary that is an accepted trade — the API-key surface (`environ`, `mem`, ptrace, signals) is provably blocked, and the alternative (`real-proc`) buys PID-metadata hiding only at the cost of `CAP_SYS_ADMIN` on the outer container, a larger blast radius.

Because the no-leak property is a kernel fact rather than a typeclaw invariant, the consumer **probes** it before ever selecting `proc-bind` (`canBindProcSafely`, `src/sandbox/availability.ts`): it spawns a sentinel sibling in the parent userns holding a planted secret, enters the exact `proc-bind` bwrap shape, and asserts the sentinel's `environ`/`maps` are unreadable and it is unsignalable, while the sandbox's own `/proc/self/{fd,maps}` are readable. A host where any of those fail (an exotic runtime that preserves parent-userns creds) fails the probe and falls through to `--tmpfs /proc` — fail-closed, never a silent leak.

### `sandbox.realProc`: opt-in PID isolation via a fresh procfs

`typeclaw.json#sandbox.realProc` (default `false`) opts into a **two-phase** form that adds full PID isolation on top of the environ guard:

```
unshare --pid --fork --mount --mount-proc -- \
  bwrap --unshare-user --unshare-ipc --unshare-uts --unshare-cgroup [--unshare-net] \
        … --ro-bind /proc /proc … bash -c <command>
```

The outer `unshare` creates a new PID + mount namespace as real root and mounts a fresh procfs **scoped to that PID namespace**. bwrap then runs inside it and must NOT re-unshare pid (a second PID ns with no matching procfs reintroduces the crash), so it unshares every namespace _except_ pid explicitly instead of `--unshare-all`. Because the new procfs only contains the sandbox's own process tree, `--ro-bind /proc /proc` binds that scoped view — the agent runtime's pids are simply **absent** from the namespace (not merely unreadable, as under `proc-bind`), so even the non-secret PID metadata is hidden.

Two constraints make this opt-in rather than default. First, `unshare --mount-proc` needs real `CAP_SYS_ADMIN`; `planStart()` requests it only when `realProc` is set, but the production entrypoint's non-root UID and empty capability set mean the request currently does not survive to the agent. Second, OrbStack rejects the mount even in environments where the cap survives. The container-side `canMountRealProc()` probe therefore falls back to `proc-bind` whenever the mount is unavailable. The net: `realProc: true` only selects `real-proc` on a runtime where the capability actually reaches the process and the mount works.

### Strategy resolution order

`applyBashSandbox` (`src/agent/plugin-tools.ts`) picks per container boot: `real-proc` if `sandbox.realProc` is set AND `canMountRealProc()` (the cap-mount works) → else `proc-bind` if `canBindProcSafely()` (the no-leak probe passes) → else `--tmpfs /proc` (degraded; external packages unavailable). Both probes are cached process-globally, and the strategy is read from the boot-time `config` snapshot (not live `getConfig()`), so it stays coherent with the boot-time `--cap-add=SYS_ADMIN` decision across a `typeclaw reload`.

The `proc-bind` no-leak probe is a security check, not a capability check: it can return `inconclusive` (a probe timeout under a boot-time load spike, a sentinel race) which proves nothing about the host. `resolveProcStrategy` retries an `inconclusive` verdict on a staggered backoff (`PROC_BIND_RETRY_BACKOFF_MS`, `src/sandbox/availability.ts`) before degrading, so a transient hiccup on a capable host does not silently fall to `--tmpfs /proc` and break allowed `bunx`/`bun run` execution. A definitive `unsafe` (a real cross-userns leak) still fails closed immediately with no retry.

When the strategy _does_ resolve to `--tmpfs /proc` AND an allowed command needs a real `/proc` (`commandNeedsRealProc` — `bunx`, `bun x`, `bun create`, or `bun run`), `applyBashSandbox` throws _before_ running it, so the agent gets an actionable message instead of Bun's opaque `NotDir`. Which error it throws depends on **why** it degraded — `resolveProcStrategy` returns the reason alongside the strategy:

- **`definitive`** — the probe returned a proven `unsafe` (a real cross-userns leak). This is the **only** verdict the probe can establish as permanent, so it is the only `definitive` degrade: it fails closed for good and throws `SandboxDegradedProcError` ("this is an environment limit; retrying will not help"). It is also the only path that emits the once-per-process `[sandbox] degraded /proc mode` warning.
- **`unverified`** — the safety probe never reached a definitive verdict within its retry budget. This covers **both** a transient boot-time CPU/IO storm (e.g. several containers starting at once, tripping the probe's own timeout) **and** a durably-incapable host (no usable namespaces, or a bwrap that starts but cannot set up its sandbox). The probe cannot prove a _negative_ capability — only a leak is definitive — so an incapable host is not distinguishable from brief saturation and lands here too. This throws `SandboxProcProbeUnverifiedError` ("this is almost certainly temporary; retry the same command in a few seconds"), the opposite guidance. Because `inconclusive` is never cached, the **next** bash call re-probes from scratch: a capable-but-saturated host promotes to `proc-bind` once the spike passes, while a genuinely incapable one simply re-degrades each call (a cheap re-probe, never a permanent pin). Without this split, a single unlucky boot-storm probe degraded a fully-capable container and told the agent it was a permanent limit, so it gave up instead of retrying — leaving `bunx`/`bun run` broken until a manual `typeclaw restart`.

### Re-exposing `/proc/self/exe` (the `--tmpfs /proc` fallback only)

Under the degraded `--tmpfs /proc` fallback (reached only when both `real-proc` and `proc-bind` are unavailable), one `/proc` entry **is** re-exposed: `/proc/self/exe`. JS package runners (`bunx`, and node's `npx`/`pnpx`) read it to locate their own interpreter — under an empty `/proc` that read fails and `bunx` panics in `createFakeTemporaryNodeExecutable: error.FileNotFound`. The sandbox resolves the running bun binary on the host (`process.execPath`, the concrete ELF `/proc/self/exe` would point at) and, after `--tmpfs /proc`, emits `--ro-bind <bun> <bun>` plus `--symlink <bun> /proc/self/exe`. Only that one symlink is restored; `/proc/N/environ` and the rest of `/proc` stay masked, so the `OPENAI_API_KEY` leak the `--tmpfs /proc` guard prevents is untouched.

A bare `--ro-bind /proc/self/exe /proc/self/exe` does **not** work and is the trap to avoid: bwrap resolves bind sources at setup time, when `/proc/self` is bwrap's own pid (it runs as PID 1 in the new namespace before forking the child), so the bind would capture the bwrap binary, not the runtime. The concrete-path + `--symlink` idiom is the only correct form. See `src/sandbox/build.ts` (the `procSelfExe` branch) and `resolveProcSelfExe` in `src/sandbox/availability.ts`.

The restored target is always the **bun** binary, and that is correct **only because the container is bun-centric**. The base image (the pinned `oven/bun` slim tag) ships no real `node`: `node` is a symlink to bun, and `bunx`/`npx`/`pnpx` all resolve to bun via [Bun's fake-node model](https://bun.com/docs/pm/bunx) (Bun creates a temp `node` shim pointing at itself and prepends it to `PATH`). So every process that reads `/proc/self/exe` inside the sandbox _is_ bun — pointing it at bun is accurate, not a hack. The one case this would be wrong is a **real** `node` binary installed into the image and run without `--bun`: that process would read `/proc/self/exe`, get bun's path, and mis-resolve `process.execPath` (breaking `child_process.fork`, worker threads, and self-re-exec). The image does not include node today; if that ever changes, `resolveProcSelfExe` must resolve the actual interpreter per invocation instead of always returning bun.
