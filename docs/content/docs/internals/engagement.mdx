`src/channels/router.ts` decides, for every admitted inbound message, whether the agent wakes up and replies. The decision logic lives in `src/channels/engagement.ts` (`decideEngagement`); the router wires it to the prompt queue, the context buffer, and the inbound broadcast. This page documents the runtime concept — the operator-facing config knobs (`trigger`, `stickiness`, `alias`) are in the [channel-adapters reference](/docs/reference/channel-adapters) and the `typeclaw-config` skill.

## The four-way decision

Every inbound that survives the `channel.respond` permission gate is tagged with one of four decisions. The router publishes the tag on a `channel-inbound` broadcast event (`publishInbound`, `router.ts`); `typeclaw inspect` renders it as a colored `[...]` prefix (`src/inspect/render.ts`).

| Decision  | Meaning                                                      | Inspect color |
| --------- | ------------------------------------------------------------ | ------------- |
| `engage`  | Reply — message enters `promptQueue`, the drain loop prompts | green         |
| `observe` | Don't reply, but remember — message enters `contextBuffer`   | dim           |
| `denied`  | Blocked by the `channel.respond` permission gate             | red           |
| `claim`   | A `claim-…` role-claim code; handled before engagement       | magenta       |

`denied` and `claim` are decided in `route()` _before_ engagement runs. `decideEngagement` itself only ever returns the narrower `EngagementDecision = 'engage' | 'observe'` — that is the union to extend if you add a wake-up reason. The wider four-way `InboundDecision` (`src/inspect/types.ts`) is the broadcast/protocol surface; both unions are currently spelled inline in `engagement.ts`, `inspect/types.ts`, `shared/protocol.ts`, `router.ts`, and `server/index.ts`. Adding a fifth decision means touching all five.

## The engage ladder

`decideEngagement` is a priority ladder. The first matching rule wins; falling off the bottom yields `observe`.

1. **Explicit triggers** (config `trigger`): `dm`, `mention` (platform `<@id>`), `reply` to a bot message. Any one engages.
2. **Sticky credit**: if `stickiness` is on and the author holds an unexpired credit in the `StickyLedger`, **consume** it and `engage` — for the full window (default 15 min). Credits are granted to the authors a bot reply targets (`grantStickyForReplyTargets`), so a back-and-forth stays engaged without re-mentioning. The credit is one-shot (consumed even when it engages), so a fresh reply must re-grant it; a stale credit can't resurrect a later turn. This gate is deliberately **content-blind**: it answers "am I mid-conversation with this author?", not "does this message need a reply?" — a boolean over membership can't tell `"where did you send it?"` (reply) from `"lol ok"` (chatter). Selectivity for plain chatter in a busy room is the **model's** job, applied via the group-chat nudge below, not the gate's. (This intentionally supersedes the earlier _wholesale_ group-suppression of sticky, which dropped genuine follow-ups outright.)

   **Multi-human target pre-check** (`effectiveHumans > 1` only): in a busy group the conversational target shifts every message. Before sticky consumes, `decideEngagement` runs the same **structural** "addressed to someone else" test the fallback suppressors use (`mentionsOthers`, `replyToOtherMessageId && !botInThread`, `textTargetsAnyPeerBot`, factored into `targetsSomeoneElse`). If the credited author's _current_ message is structurally aimed at a third party — `@bob what do you think?`, a reply to another human, or a peer bot by name — return `observe` **without consuming the credit**, so the credit survives for that author's next untargeted follow-up. A plain follow-up (no suppressor set) falls through and engages exactly as before. This stays inside the content-blind rule: it adds **no** semantic text interpretation, only reuses adapter-classified structural booleans and reorders them ahead of the credit. It is gated on `!matchesAnyAlias(text, selfAliases)` so a message that also names us by alias still engages on rule #3 (the multi-bot `토토아 라라아 둘 다 봐` case). Solo-human channels (`effectiveHumans <= 1`) are excluded — there the sticky-over-`mentionsOthers` behavior is intentional and tested.

3. **Alias match**: the message text contains the agent's name or a configured `alias` in plain text (case-insensitive substring, no word boundaries). `basename(agentDir)` is an implicit alias. **Not** suppressed by `mentionsOthers` — addressing two bots by name in one message engages both, each on its own alias.
4. **Suppressors** (see below) — if any fires, return `observe` even though the solo-human fallback would otherwise engage.
5. **Solo-human fallback**: if the channel currently holds at most one distinct **human** participant and the author isn't a bot, engage. Reverts to strict the moment a second human posts. This makes a one-human dev channel work without an `@mention` on every line.
6. **Default**: `observe`.

## Clearing stickiness (`channel_disengage`)

Sticky credit normally drains on its own — consumed on the next inbound, expired on TTL (default 15 min), or lost on a container restart. There is no other natural exit, and because every reply **re-grants** a fresh credit (`grantStickyForReplyTargets`), a bot in a busy multi-bot room can stay engaged turn after turn even after a participant tells it to stop.

`channel_disengage` is the runtime escape hatch. It calls `ChannelRouter.clearSticky(key)`, which drops every credit for the channel key via `StickyLedger.clear` and returns the bot to strict rules #1/#3 engagement (mention / reply / dm / alias) for that conversation. It sends no message, is scoped to the one channel key, and is in-memory only — a later reply re-grants normally, so it is a "drop in, then resume" action, not a permanent mute.

The same-turn re-grant is the subtle part. The agent's natural pattern is to **ack and disengage** ("ok, backing off"), but that ack is itself a `channel_reply` whose success path would re-grant the credit `clearSticky` just dropped. To keep disengage binding, `clearSticky` stamps `live.disengagedTurn = turnSeq`, and `send()` **skips** `grantStickyForReplyTargets` while `disengagedTurn === turnSeq`. The suppression is scoped to that one turn (matched by `turnSeq`, reset at turn start), so the next turn re-grants as usual. This mirrors the `skip_response` send-lock shape: a turn-local flag that makes "I'm stepping back" survive a same-turn reply.

## Suppressors

The suppressors exist to keep the bot out of conversations clearly aimed elsewhere, _before_ the permissive solo-human fallback can fire. Each is populated by the adapter classifiers and flips the fallback off for one message without changing channel state. Explicit triggers (1–3 above) are unaffected — they engage even when the message also tags a third party.

- **`mentionsOthers`** — the message tags at least one other user and none of the mentions resolve to us.
- **`replyToOtherMessageId !== null && !botInThread`** — the message is a reply to a message we didn't author, and we haven't sent into this thread yet. `botInThread` (router: `live.successfulChannelSends > 0` or a bot-authored buffered message) is the escape hatch: Slack's `parent_user_id` is the **thread root** author, so a thread a human starts by @-mentioning the bot would otherwise drop every follow-up reply once the bot is in it.
- **`textTargetsAnyPeerBot`** — the message's text contains a known peer bot's observed display name. Each bot configures only its own aliases, so peer names come from `participants[]` (set once a peer has spoken); a never-seen peer's first addressing slips through, then is caught forever.

### Peer-bot philosophy (do not relitigate)

Peer bots remain reachable through the **same** triggers as humans (mention / reply / dm / sticky). They are _not_ downgraded to mention-only, and there is no `peerBotTriggers` knob. Bot-to-bot conversation is a first-class use case here. What peer bots do **not** get is the solo-human fallback — that courtesy is for humans who don't want to type `@bot` in their own channel. Letting peer bots ride the fallback produced multi-turn bot-to-bot introductions after a single human "얘들아". The fix was to close the fallback for bots, not to firewall bots behind explicit mentions. The full rationale is pinned in the comment block above the suppressors in `engagement.ts`.

## Membership and the human count

The solo-human fallback counts humans. Persisted `participants[]` (speakers seen in the last ~7 days) is the baseline; `resolveEffectiveHumans` (`engagement.ts`) reconciles it with a `MembershipCount` from the adapter's member API (`src/channels/membership.ts`):

- A **fresh, complete** read (`!truncated && now - fetchedAt < MEMBERSHIP_FRESHNESS_MS`, 60s) is ground truth — it sees lurkers and prunes leavers.
- A **truncated or stale** read is a quieting hint only: `max(persistedHumans, membership.humans)` avoids under-counting active humans.

The router invalidates and warms the membership cache when a previously-unseen author posts, so the _next_ turn sees fresh data while the current turn still gets a fast answer.

## observe: watch but remember

`observe` is not a dead end. When the router gets `observe` (`route()`):

1. **Broadcast + log.** `publishInbound(event, 'observe')` emits the inbound event; the router logs `observed id=…` so an unanswered mention is diagnosable from logs alone (the bracketed shape mirrors `prompting batch=` for log scraping).
2. **Buffer.** `observe(live, event)` pushes the message into `live.contextBuffer` (an `ObservedInbound`), capped at `CONTEXT_BUFFER_SIZE` (20) by trimming the oldest.

The buffer is consumed by four readers:

- **Next engaged turn.** `drain()` splices the entire buffer alongside the prompt batch into `composeTurnPrompt`, which renders it under `## Recent context (not addressed to you, for awareness only)` — distinct from `## Current message(s) (addressed to you)`. So when the bot finally engages, it catches up on everything it silently watched.
- **Attachment resolution.** `resolveInboundAttachment` / `listInboundAttachmentIds` walk `promptQueue` **and** `contextBuffer`, newest-first, so an observed photo is still referenceable by `attachment_id`.
- **Quote anchoring.** A tool send refreshes its quote candidate against `contextBuffer` to detect channel chatter that landed between the inbound and the reply (`refreshQuoteCandidate`). See [channel-adapters](/docs/reference/channel-adapters) for the user-visible blockquote behavior.
- **`botInThread`.** `hasBotParticipated` scans the buffer for a bot-authored message to decide the `replyToOtherMessageId` suppressor.

Cold-start prefetch seeds the same buffer (`source: 'prefetch'`), and may exceed the cap on the one-shot seed; subsequent `observe()` calls trim back to 20.

### Known asymmetry

The `contextBuffer` only flushes inside `drain()`, which only runs on an `engage`. A channel the bot perpetually observes (a busy multi-human room it's never addressed in) trims **by count only**, never by age. There is no staleness gate on flush, so the first engage after a long observe-only stretch can inject up-to-20 stale messages as "recent context." Prefetch is bounded by recency; runtime observation is bounded only by count. Whether this matters is a product call — noted here so a future maintainer doesn't assume the buffer is time-bounded.

## Peer-bot loop guard

Distinct from the per-session [tool loop guard](/docs/internals/message-stream) (`src/agent/loop-guard.ts`, exact-call and sliding-window cycle detection). The channel-level guard (`updateLoopGuard`, `router.ts`) counts **engaged peer-bot turns since the last human**:

- Any human inbound resets the counters and clears `loopGuardActive`.
- A peer-bot engage increments `consecutiveEngagedPeerBotTurns` and pushes onto a sliding `PEER_BOT_TURNS_WINDOW_MS` (60s) window.
- Tripping `MAX_CONSECUTIVE_PEER_BOT_TURNS_SINCE_HUMAN` (5) **or** `MAX_PEER_BOT_TURNS_IN_WINDOW` (5 in 60s) sets `loopGuardActive`.

When active, `composeTurnPrompt` prepends a fenced `**[SYSTEM MESSAGE — not from a human]**` block telling the model it may reply `NO_REPLY` to stay silent. The notice lives in the user-turn suffix (not the system prompt) so it stays cache-neutral, and clears automatically once a human posts.

## Group-chat nudge

A second, milder runtime notice rides the **same** fenced `**[SYSTEM MESSAGE — not from a human]**` convention. On any engaged turn in a multi-human group (`live.multiHumanGroup`, set in `route()` from the same membership + participants the engagement decision used), `composeTurnPrompt` appends a block telling the model it is woken on every message from someone it recently talked with, and should reply only when addressed or directly continuing its own last exchange — otherwise `NO_REPLY` / `skip_response`, preferring silence when unsure. It is suppressed when the loop guard already fired (one silence notice per turn), and like the loop guard it is a cache-neutral user-turn suffix.

This nudge is **load-bearing**, not a backstop. Because sticky now engages every group follow-up (rule #2 is content-blind), the nudge is the **only** thing that keeps the bot from answering chatter in a busy room — the gate gets the bot into the turn; the model decides whether to speak. Removing the nudge would reintroduce group spam. `isMultiHumanGroup` is the single definition shared by `route()` (to set `live.multiHumanGroup`) and the nudge gate, so they never disagree.

## Continuation promises while a child runs

After a terminal `channel_reply` promises more work without `more_work_this_turn: true`, the router normally queues one willingness reminder. An explicit `NO_REPLY` on that reminder triggers empty-turn recovery. Both decisions check for a running background child anywhere in the session, including one started before a later queued user message: the child's completion reminder owns the deferred result, so the router neither re-nudges its status reply nor posts a false stuck-reply warning.

This exception uses the existing stuck-child backstop. Once it expires, willingness recovery resumes. Ordinary empty-turn recovery remains scoped to the logical turn that started the child; unrelated later turns still recover, and real prose is still delivered while a child runs.

## Waiting reaction ownership

The router, not a returned reaction-instance ID, owns temporary engagement eyes and continuation hourglasses. `src/channels/waiting-reactions.ts` synchronizes one JSON record per authenticated account, canonical target, and emoji under `channels/waiting-reactions/` before calling the adapter to add it. Preparation captures the authenticated adapter's add capability, so an adapter replacement cannot add as a different account under the old tuple. Owners carry a boot epoch and generation; tuple lanes serialize adds and removals and recheck current ownership before transport. A stale callback can release only its captured owner.

At boot, cleanup releases old-epoch **temporary** owners and ensures that the original account's reaction is absent where the adapter supports own-reaction removal. A new owner on the same tuple preserves or restores presence. Review and deferred-work acknowledgments use protected owners with a durable identity covering conversation, canonical target, emoji, and acknowledgment kind: temporary cleanup and reboot never retire them merely because their epoch is old. A later genuine reply in that conversation retires matching acknowledgment owners, including those from a previous runtime, using their captured identities and generations. Acknowledgments acquired after that reply's retirement decision are not swept into it. When an acknowledgment replaces an engagement indicator on the same tuple, durable ownership conversion avoids removing protected presence.

Adapters own canonical target, emoji, authenticated identity, and own-actor removal semantics. Identity changes block cleanup rather than deleting a different account's reaction. Unsupported adapters and permission, rate-limit, or transient failures leave a recoverable cleanup record. The router does not await cleanup transport before replies or interruption notices. Filesystem work still shares the event loop: recovery yields between bounded batches, does not rewrite unchanged records, and retires ensured-absent records once no owner or live reservation references them. Missing files make stale releases no-ops; a new owner creates a fresh capability. Protected and unresolved records remain retained.

If intent storage fails, the waiting add is skipped. JSON replacement synchronizes the file and parent directory on POSIX. Windows development compatibility keeps file synchronization but explicitly skips unsupported directory synchronization; it does not promise power-loss durability. Other synchronization errors propagate. This assumes one runtime writing an agent directory, not concurrent runtimes or remote-call fencing.

## Durable inbound admission and turn ownership

`src/channels/inbound-journal.ts` is the router's single-writer authority for
engaged inbound requests and mixed inbound/background decisions. It appends one
versioned transition per synced line to `channels/inbound-continuity.jsonl`.
Observe, denied and control traffic creates no response obligation.

`route()` returns an admission receipt: `accepted` with a stable input ID and
generation, `duplicate` with the original input ID and outcome, or `observed`,
`denied` or `control`. Acceptance is durable before publication, reactions,
enqueueing or return. Identity includes the agent directory, authenticated
account, exact channel key, external message ID, event kind and revision, so
GitHub review rounds are not collapsed into a generic PR ID.

Slack (`slack` and `slack-bot`) engages at most once per message. The journal
keeps a per-message index over agent directory, authenticated account, adapter,
workspace, chat, message `ts` and event kind. Routing thread and revision are
not part of it. A later delivery of an already-admitted message, whether an
edit, a copy routed to a mention thread or a twin event, returns `duplicate`
with the existing input ID and outcome. Its obligation and target stay where
they were and do not move to the new thread. The same message from a different
author is rejected as a conflicting principal instead of opening a new slot.
The index is rebuilt in memory on load and admission from open rows and from the
message key kept in closed tombstones, so it survives compaction and restart. Rows written per edit
revision by earlier versions are all kept: the earliest one represents the
message, and none is merged or cancelled. Rows recorded under a different agent
directory path do not match.

An observed, unengaged Slack message can still engage once when an edit adds a
mention. The adapters decide edit eligibility before normalization, command
handling or routing. A raw `message_changed` envelope qualifies only when its
previous text lacks an explicit self or group mention, its new text has one,
and it carries a platform edit revision. On `slack-bot`, an `app_mention` with a
valid edit marker that explicitly addresses the bot also qualifies, without the
previous text. That is a first-engagement fallback, not proof that the mention
was newly added. Typo and other content edits, unchanged or removed mentions,
unfurl/metadata-only updates and flattened edits without proof are dropped. A
known edit that contains a command or claim code, as recognized by the real
command and claim parsers, is dropped before any handler runs. An `app_mention`
without an edit marker is indistinguishable from an original. It follows the
original path, where recognized commands are handled before the journal, so
control traffic has no exactly-once guarantee. These checks are stateless, so a
restart or cold dedupe cache does not widen them. Other adapters keep
per-revision identity.

Queues cache IDs rather than generation snapshots. The target lane resolves
current ownership and commits a turn claim before splicing, todo updates,
prompting or tool dispatch. Retries retain their claim; a reload handoff or a
deferred-work carry moves ownership rather than copying or deleting an
obligation. A confirmed terminal reply or review covers only its captured
IDs. A substantive `channel_send` to
the turn's exact origin coordinate (adapter, workspace, chat and thread; a root
post does not match a thread origin) also settles the invoking session's
captured inbound and fetched background coverage once the send lands and the
captured generations still match. It remains non-terminal: the turn continues,
and no terminal-reply stop is recorded. Status or progress sends recognized as
continuation willingness, successful no-ops without delivery, failed sends,
off-target sends and sends from another session never settle that coverage. A
send that landed before a local settlement failure is not re-sent; the
coverage stays owed for conservative recovery. Healthy inbound-only `NO_REPLY`
explicitly records intentional silence; SDK stop, child completion and recovery
`NO_REPLY` are not delivery or background suppression. `NO_REPLY` after the
turn's last origin output was a promise (a progress `channel_send` or a
`channel_reply` with `more_work_this_turn: true`, in any language) does not
settle either: the promised work is still owed.

A provider-error notice (`⚠️` plus the redacted provider message) is a terminal
outcome for the requests its turn owned. The router captures the turn's owned
inbound refs before sending it and settles exactly those refs at the captured
generations once the send is confirmed. It never settles consumed or fetched
background results. A failed or no-op send settles nothing, and a settlement
write failure is logged without replaying the turn; the debt stays owed.

When a logical turn ends with owed coverage and no provable continuation (no
queued retry, no running child the coverage is deferred on, nothing queued),
the router transfers that coverage at once to a **live-turn-ended** notice in
the same target lane. It is imported into the same recovery outbox, and the
running dispatcher delivers it without waiting for a restart. A later,
unrelated input never absorbs it: a fresh "Thanks!" turn settles only its own
request. Idle eviction pins coverage that awaits a running deferred child (up
to the stuck-child backstop). Otherwise it transfers remaining owed coverage
as a live-turn-ended notice before teardown; a failed transfer skips eviction.
If preparation committed but outbox publication or source ownership failed,
the next applicable in-lane lifecycle or consume decision resumes that frozen
transfer unchanged. Cached identities stay reachable until ownership completes,
including across failed reloads and handoff discard attempts. A later input
never joins that frozen coverage, and recovery does not replay the model or tools.
Stale-session rollover instead passes coverage through the bounded reload
handoff to its successor, whose first in-lane consume moves deferred coverage
or transfers abandoned coverage. A refused handoff reports a live-turn-ended
transfer and retains its retry identities if that transfer fails.
Account-mismatch transfers, reload transfers of non-deferred coverage and
handoff expiry or capacity transfers also use the live-turn-ended cause.
An actual source-journal write failure still freezes continuity; it is not an
outbox-only failure that the running process can repair. Router shutdown transfers nothing; that
debt stays owed for boot recovery after the restart.

A fresh input that arrives while the previous turn's coverage is deferred on a
background child does not by itself abandon that coverage. When the same drain
also consumes an eligible durable completion of that deferred work, the
previous coverage moves into the coalesced turn even if the registry no longer
reports the child running. An eligible completion is a real result-ready,
unclaimed and untransferred obligation for the exact target. Its parent must be
the session the coverage was deferred from or its current claim owner, its
account must match, and it must have been accepted no earlier than the start of
the deferred interval. Generic wakes and stale, closed, transferred,
wrong-parent, wrong-account or earlier-turn completions are not carriers; a
genuinely abandoned earlier turn has already transferred to a live-turn-ended
notice when it ended.

Deferred coverage is the turn's open requests, the child results it already
consumed, or both. A completion-only turn that consumed one child's result and
then waited on another child defers that result the same way, with no inbound
row. Before the carrying turn's first prompt, one journal decision moves the
requests and consumed results out of the source turn together, and the moved
results stay in the new turn's coverage beside newly claimed completions, so its
final reply closes all of them. A cached ID is only a locator: a row moves only
while its current claim still names the recorded source turn and owner at the
row's current generation, target and account. Without a running child of those
sessions or an eligible completion, a fresh input transfers a consumed result to
the notice outbox like an abandoned request, and a wake-only drain leaves it with
its source turn for durable recovery instead of acquiring it.

Different authors may share a turn without losing their immutable permission
principals. Interruption notices partition coverage by exact channel key,
authenticated account, canonical principal and effective captured parent
session (`recoveryNoticePartitionKey` in `src/channels/recovery-notice.ts`);
turn ID, text and timing never merge partitions. `/stop` can withdraw every
partition for that parent.
Stop partitions active and queued inbound/background coverage by authenticated
account before committing suppression, so a rotated account's queued request
cannot invalidate withdrawal of the old account's active request.
An account replacement does not inherit the old actor's accepted work: mismatched
coverage transfers under its original identity, while compatible new input can
continue. Replies and formal reviews retain the captured account fence through
the selected sender rather than trusting a replacement adapter's credentials.
The router captures the teardown generation before asynchronous journal and
account checks; an inbound invalidated by teardown cannot install a later session.

Mixed transitions validate complete coverage inside the target lane and follow
this order:

| Decision                                    | Durable order before cache/dispatch changes                                                                    |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Claim or ownership move                     | Journal decision → background JSON applications with matching generation/digest receipts → journal all-applied |
| Reply, review, origin send, skip or `/stop` | Journal outcome → idempotent background settlement/receipts → all-applied → clear/abort                        |
| Interruption transfer                       | Journal preparation → required JSON applications/receipts → all-applied → outbox import → source ownership     |
| Confirmed interruption                      | Outbox receipt → journal source closure and required JSON applications → all-applied                           |

`bootBackgroundObligations` (`src/run/background-handoff-boot.ts`) runs the whole
continuity boot sequence before adapters start. The journal folds and repairs
committed mixed decisions, then re-imports every already-issued inbound or mixed
transfer unchanged, once per delivery ID, before grouping new work. Remaining
older-epoch open requests are grouped by notice partition, where the effective
parent is the claim owner or else the admission parent; compatible untransferred
older-epoch background obligations join the same partition, and `prepareNotice`
rejects a child whose effective parent differs. Inside each target lane, boot
revalidates current generations, orders refs deterministically, prepares one
mixed notice through the journal and imports it to the fixed-notice outbox.
Legacy migration and the background-only fallback for unmatched children run
afterward; adapters, the restart greeting and the dispatcher wake follow.
Current-epoch work is not swept, closed rows and issued singleton, mixed or legacy
transfers are never regrouped, and late matching rows get their own notice.
If any step fails, boot freezes the background store, logs that continuity is
blocked pending operator repair, and still starts adapters and the dispatcher:
independent verified notices continue, while journal- or background-dependent
notices fail closed at dispatch validation. Boot never reopens a transcript to
re-prompt interrupted work.

A config, role or provider reload, whether the session is idle or mid-drain,
keeps coverage that is deferred to background work (a running child of the
deferring turn, or its completion wake already queued) in the bounded reload
handoff. The handoff stores the IDs, source turn, owner, captured account and
author, and counts toward the existing item, byte, key and expiry limits. Other
open coverage transfers at reload as a live-turn-ended notice. The handoff recreates a
successor session even when no queued input remains, without a synthetic
prompt. A completion that arrives before the successor is installed is held on
the handoff only if it fits the existing per-key item, per-key byte and global
byte limits. Otherwise the error is logged, the handoff stays as it was, and
the result remains owed for durable recovery. The successor's target lane
revalidates and moves durable ownership before its first real prompt. Restored
IDs grant no ownership by themselves: the successor checks them against the
recorded source turn and owner and that deferral's child, which may belong to a
session ID other than its own. Coverage
whose account no longer matches transfers under its original account before
retention, so no successor inherits it. `/stop` (text or native slash) with no
live session withdraws a pending handoff that holds owed or queued work
(queued inputs, completion reminders or deferred coverage). A handoff that
carries only observed context, such as an idle bystander conversation, is
ignored. The slash command returns no-live-session, text `/stop` stays quiet,
nothing is withdrawn and no "Stopped" reply is posted. A thread-less slash
command resolves the conversation's handoff only when exactly one qualifies, and
otherwise reports ambiguity. Inside the target lane, the handoff's queued and held work is
settled as intentionally suppressed per account before the owed work is
dropped. If settlement fails for any account, the whole handoff is kept. Observed context is kept for
the next session, as with a live stop. No session or provider is created, and
pending notices for that session are withdrawn. Expiry or capacity
overflow transfers the coverage as a live-turn-ended notice under its original principal and account; a
failed transfer keeps the handoff for retry, and a later reload recreates
successors for handoffs that are still pending.

### Storage failure and operator recovery

Write or sync failure rejects admission visibly and synchronously cancels active
channel SDK loops, preventing new tool dispatch and follow-up provider requests;
an already-running side effect cannot be recalled. Memory cannot authorize
progress. Journal corruption freezes all
background obligations and any background/inbound-covered outbox record because
an unapplied mixed decision may have left no hint in child JSON. A valid-looking
record, different target or absent receipt is not proof of independence.
Verified inventory-only notices with entirely JSON provenance may still progress.
`/stop` still aborts a live parent when durable withdrawal fails; unresolved
coverage remains owed for conservative recovery.
The dispatch fence rechecks stop intent after asynchronous account validation
and before every provider attempt, so a stopped batch cannot start behind the
abort. Failed bootstrap cleanup releases the journal writer before a later boot.

Router shutdown cancels unfinished journal initialization before asynchronous
teardown. Canceled startup releases writer ownership without reopening a removed
state directory or reporting a continuity failure. An already-initialized journal
remains writable for durable teardown decisions until its final close.

An incomplete final line is truncated and synced through a non-append repair
handle before opening the append writer, including on Windows.
A complete malformed line, unknown schema version, invalid generation or
mid-file corruption preserves the bytes and reports a recovery error instead
of dispatching. Operators must stop the runtime, preserve a copy of the journal
and related JSON, repair or restore the authoritative journal, then restart.
Deleting the journal or the child JSON is not a safe repair: it can erase a
committed cancellation or authorize duplicate work.

Maintenance is automatic. `startAgent` starts journal maintenance
(`InboundJournal.startMaintenance`) after the boot continuity step, including
when that step failed. A frozen or closed journal is never rewritten: a queued
compaction is skipped. `close()` stops maintenance; a queued compaction that has
not started is skipped, and one already in progress finishes before the handle
closes. A
compaction is queued on the writer queue when growth since the last snapshot
line (the whole file if there is none) reaches the larger of 1 MiB and the
last snapshot's size. The check runs at start and after each successful append
as a counter comparison, so retained tombstones never cause repeated rewrites
and a boot or tick without growth rewrites nothing. There is no user setting.

Normalization does not wait for compaction. Every append, and the boot fold,
turns a closed row into its tombstone and an applied decision into a receipt in
memory; only unapplied mixed decisions keep their full bodies. Boot streams the
journal one LF-terminated line at a time with fatal UTF-8 decoding. Bytes after
the last LF are a torn tail and are truncated before the writer opens; any
invalid complete line freezes the journal and keeps its bytes.

Compaction serializes with writes, syncs a same-directory snapshot, closes the
old handle before replacement, syncs the directory and reopens before resuming.
The snapshot (`schemaVersion: 2`, first line of the same JSONL file) holds each
frozen transfer payload once per delivery ID, full open rows, minimal closed
tombstones, pending mixed decisions and the retained decision receipts. A closed
tombstone keeps the input ID, generation, acceptance time, message reference, a
principal digest for the author conflict fence, the Slack message key where one
applies, the outcome and the notice delivery ID; it drops identity, principal,
claim, target, account, epoch and transfer payload. `get()`/`list()` return
that minimal shape as soon as a row closes, so replay of an old message still
returns `duplicate` with the original input ID and outcome before compaction,
after it and across reboots. Version 1 logs and snapshots stay readable.

Retention follows reachability, not age or count. Without a proven upstream
replay/checkpoint floor covering revisions, tombstones and frozen notice
payloads (once per delivery) are kept indefinitely, and unresolved obligations
never expire. Receipts are kept only while a caller could still present the
decision ID:

- Derived or caller-named IDs (`prepare:`, `owned:`, `recovery:` and stop
  decisions) are kept indefinitely.
- `admit:<inputId>` receipts are never kept, because the permanent row answers
  admission.
- Claim and move IDs that the journal minted itself are never kept.
- Bare-UUID decision IDs, such as router settlements, are kept only while the
  epoch that minted them is running. They are dropped at the next boot, since
  no durable record re-issues a bare UUID; until then the running process
  holds them in memory.

POSIX file/directory sync fences process death. Windows closes handles before
replacement but cannot promise the same directory-sync power-loss durability.

Measured once on single hosts during development (one run per configuration;
indicative, not a guarantee for other hardware or workloads):

## Background work across runtime death

`src/channels/background-obligations.ts` stores one durable owed-response record per direct background task launched by a channel-origin parent. The router accepts the response before execution; a failed acceptance prevents the child from starting. The record captures the original exact channel target, permission principal and cached authenticated account identity. Transcript filenames are optional metadata. TUI, cron, foreground children and nested descendants do not get separate background-response records.

The registry remains the authority for execution, and the transcript remains the authority for content. Canonical child completion marks an existing obligation result-ready; it does not settle the response. An absent parent, a queued completion, reminder consumption, assistant `stop`, `NO_REPLY` or provider failure leaves the response owed. **Queued is not delivered.**

Before splicing completion reminders into a prompt, the router durably claims their exact obligation IDs and generations. A successful final-result fetch attaches that task's coverage; polling a running task does not. Retries retain coverage, and a reload handoff or deferred-work carry moves ownership rather than recreating the obligation. Only a router settlement decision closes consumed or fetched coverage: a confirmed terminal reply, recognized formal review, substantive non-terminal `channel_send` to the exact origin coordinate, explicit skip or `/stop`. Progress, `more_work_this_turn`, continuation willingness, off-target sends and sends from other sessions cannot settle siblings or other turns. The durable decision precedes cache clearing or parent abort.

Live queues and turn coverage retain obligation IDs, not generation snapshots. Claim, fetch, settlement, stop withdrawal and reload retention resolve current ownership inside the same per-target lane after earlier decisions finish. A fetch retires its queued wake; a closed or already-owned wake is reconciled without replaying the result or blocking unrelated human input. `/stop` waits for an in-flight claim before selecting its coverage. If genuine storage failure prevents withdrawal, it reports the failure and still aborts the parent; the unresolved obligation remains eligible for conservative recovery.

On boot, unresolved obligations from an earlier epoch transfer to `channels/recovery-outbox/<deliveryId>.json`. An obligation that shares a notice partition with older-epoch inbound requests joins that partition's single mixed notice; the remaining obligations use the existing background-only transfer. The source freezes coverage, target, principal, delivery ID and notice payload before import; outbox import is durable before source ownership changes. A delivered interruption notice ends exactly the obligations it covers. Repeated boots repair the same transfer rather than replaying the child or asking the model to recover it. The old launch-inventory format is read only for migration, respecting already-transferred and delivered receipts before retiring legacy files. Ordinary #291 restart greetings and TUI handoff remain separate.

The dispatcher runs after adapter readiness with independent per-target lanes. Each attempt revalidates the configured authenticated account, original destination and current response/send permission. Removed credentials, permission denial and unavailable destinations leave the record **blocked and still owed**, not terminal or age-expired; another target can continue. Transient failures, including identity preflight failures, are persisted with capped backoff and server retry delays. A lease is usable only after its file and directory publication complete; visible leased bytes following a failed sync do not authorize transport. A confirmed receipt is synced before source acknowledgment. Known receipts are never reposted.

After its first boot wake, the dispatcher also wakes on every new durable
outbox import, so a live-turn-ended notice is sent by the running process
rather than at the next restart. Once a delivered or suppressed record is
acknowledged and its source validates as resolved, the dispatcher retires it
from `channels/recovery-outbox/<deliveryId>.json` to a minimal fence at
`channels/recovery-outbox/retired/<deliveryId>.json` (delivery ID, payload
digest and final dispatch state). Re-importing the same frozen record returns
that terminal state and never recreates pending work. Pending, leased, blocked
and unverifiable records (for example while the journal is frozen) stay in the
live outbox.

Admission also freezes the permission-matching origin context, including a native
thread's `parentChat` and triggering author, before asynchronous metadata lookup.
Recovery reuses that context: a thread authorized by its parent-channel grant
keeps the same permission principal without moving the notice to the parent.
Prepared transfers are validated against their source principal and never
reconstructed from a later live turn.

| Transition                                    | Decision owner and durable fence                                                                                                                                                                               |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Obligation → notice-prepared                  | Router continuity service freezes source generation, exact coverage and payload before import.                                                                                                                 |
| notice-prepared → notice-owned                | Outbox syncs the idempotent import before the source acknowledges ownership.                                                                                                                                   |
| pending / blocked / old-epoch leased → leased | Outbox checks expected generation, advances it and syncs epoch/attempt ownership before transport. Same-epoch in-flight work is never leased twice.                                                            |
| same-epoch leased → durably repaired leased   | Before reusing a failed acquisition, outbox republishes the captured lease and awaits file/directory sync without changing its attempt identity or count. This repair does not grant a second concurrent send. |
| leased → pending                              | Outbox retains owed work with capped backoff and any server retry delay after a transient failure.                                                                                                             |
| leased → blocked                              | Account, configuration, destination or permission denial retains owed work for later revalidation.                                                                                                             |
| leased → delivered                            | Outbox syncs a confirmed or reconciled receipt before acknowledgment; later boots do not send again.                                                                                                           |
| pending / blocked / leased → suppressed       | Explicit user-stop decision is synced before parent abort/clear. A concurrently landed receipt is retained without authorizing a retry.                                                                        |

Two fixed runtime notices exist, both independent of providers, `NO_REPLY`, session reopening and child execution. Boot recovery of genuinely older-epoch work (and legacy inventory migration) uses the frozen restart template, byte-identical to earlier versions:

> ⚠️ I restarted before I could confirm a reply to your earlier request. I didn't rerun it automatically — please ask again if you still need it.

Every transfer the router prepares inside a running process uses the `live-turn-ended` cause (`schemaVersion: 2` record, `recoveryNoticeCause` in `src/channels/continuity-types.ts`):

> ⚠️ My earlier turn ended before I could confirm a reply to your request. I didn't rerun it automatically — please ask again if you still need it.

The cause, locale, template version and text are frozen at transfer preparation and use the same outbox, dispatcher, authorization and reconciliation path. Records prepared before this version stay readable and immutable; a same-epoch transfer that an older version prepared with the restart template is not reclassified. This stack uses the existing English system-notice fallback only; it adds no locale selector or model language inference. Recovery sends retain transport/flood checks but do not change unrelated live-turn send counts, promise/leaf/skip state, engagement/reaction policy, typing or sticky state.

Compatibility is one-directional. This version reads journals, snapshots and outbox records written by earlier versions (schema version 1). Once it writes a version 2 journal snapshot or a version 2 live-turn-ended outbox record, earlier versions reject that state and fail closed, as they do for any unknown schema version: continuity freezes instead of being reinterpreted. Downgrading after such writes is unsupported; an earlier version cannot resume a store this version has written.

### Recovery boundary

- **Inbound and background guarantee:** unless explicitly cancelled or intentionally suppressed, a durably accepted channel request interrupted by process death eventually receives an answer or interruption notice once the runtime and authorized destination are available again. This starts at the durable admission boundary, not at upstream delivery or the first transcript entry.
- Healthy terminal replies, reviews and substantive origin `channel_send` deliveries close their exact result coverage without an extra interruption notice. A remote reply, review or send that landed before a settlement-write failure remains ambiguous: the obligation stays owed, and a later notice may accompany that answer. This never authorizes repeating the reply, review, send or logical turn. Notices contain no request content, names, transcript or provider errors, and interrupted work is never automatically replayed.
- A turn that ends with owed coverage, and an idle eviction or stale rollover that would discard it, transfers that coverage to a live-turn-ended notice in the running process (see above). A restart notice therefore means the process really died or was shut down with the debt still open; it is never produced for a same-process failure.
- Delivery is **at least once**, not exactly once. Death after a remote POST succeeds but before the local receipt is synced is ambiguous. Supported adapters reconcile the stable correlation marker against paginated history from their own authenticated actor at the exact target; a read failure or first-page miss is not proof of absence. Unknown or unsupported reconciliation eventually retries, accepting a possible duplicate notice. No ambiguous remote success authorizes replay of a reply, review or logical turn.
- Inventories written before this version, and new admissions whose cached identity was unavailable, use an unbound marker. The first authorized attempt durably binds the authenticated actor serving the original exact adapter/workspace under its lease before sending. Slack direct-message coordinates use a workspace sentinel, while account identity still uses the authenticated team/user. A later identity change blocks delivery. An unbound record cannot prove that the posting identity stayed unchanged between death and reboot.
- One active runtime per agent directory is supported. Local leases fence callbacks and reboots, not simultaneous runtimes or already-issued remote requests. JSON publication syncs the file and containing directory on POSIX; Windows development cannot provide the same directory-sync power-loss guarantee. Unresolved records stay in the live outbox; terminal records are retained as minimal retired fences.
- `/stop` durably withdraws current parent coverage before abort/clear, including frozen prepared transfers whose outbox publication never succeeded. A partially published notice then validates as resolved, not sendable. Stop before dispatch prevents the notice; a remote POST already in flight cannot be recalled and may land after stop. Concurrent suppression remains durable and an ambiguous suppressed send is never retried. Running descendants retain their existing independent completion policy.
- Reaction cleanup is independent work. Persisted trigger targets are not removable reaction-instance refs, and this outbox does not restore or delete temporary reactions.

## Rules of thumb

- **`decideEngagement` is pure.** Inputs in, `engage`/`observe` out. No I/O, no side effects — the router owns buffering, broadcasting, and membership warming.
- **The fix for over/under-engagement is `trigger` + `alias`, not new gates.** The `trigger` set already applies symmetrically to humans and bots. Don't add bot-only suppression knobs. Keep the engagement gate **content-blind** — it decides _whether the bot is in a conversation_, not _whether a given message deserves a reply_. The latter is a semantic call the boolean can't make; push it to the model via the group-chat nudge. Gating sticky off in groups _wholesale_ to silence chatter was tried and reverted: it couldn't tell a real follow-up from banter and dropped both. The multi-human sticky pre-check is **not** that reverted change — it does not silence chatter (the nudge still owns that), it only steps aside when an _adapter-classified structural_ signal says the message is addressed elsewhere, and it preserves the credit so the next plain follow-up still engages. Reusing existing structural booleans is content-blind; inferring intent from text would not be.
- **`observe` is logged and broadcast on every hit.** An "unanswered mention" is always diagnosable from `typeclaw inspect` or the container logs — never silent.
- **Observed messages re-enter the next turn.** Treat the context buffer as "what the agent saw while quiet," not as discarded traffic.
- **Two loop guards, two layers.** Tool-call loops are per-session in `src/agent/`; peer-bot engage loops are per-channel in the router. Don't conflate them.
