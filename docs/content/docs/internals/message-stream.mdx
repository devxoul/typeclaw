`src/stream/` is the in-process pub/sub coordination primitive. Keyed by typed targets. **Ephemeral** — Bun process crash loses stream queues. Durable recovery belongs to the decision owner outside the stream: the router's inbound JSONL journal and background-response JSON obligations transfer interrupted work into the runtime recovery outbox. **Queued is not delivered:** publishing, consuming or prompting a message does not confirm a response. Agentic work is not resumed mid-LLM-call or replayed after death.

## Targets

Four typed kinds:

- **`broadcast`** — fan-out (mood, status, presence). WS server forwards to connected TUIs.
- **`session: { sessionId }`** — addressed to a live `AgentSession`. WS server publishes; per-session drain loop subscribes.
- **`new-session: { subagent }`** — spawn a subagent. Published by cron consumer (when a `prompt` job has a `subagent` field) and the WS server (idle → memory-logger). Consumed by `SubagentConsumer`, which validates payload against `payloadSchema` and invokes the registered handler. Coalescing uses `inFlightKey(name, payload)` within the trusted parent-session scope when present, or process-wide when no parent exists.
- **`cron: { jobId }`** — fired by the scheduler. `CronConsumer` dispatches to prompt/exec runner and handles per-jobId coalescing.

Adding a fifth kind is a deliberate design choice. No generic `handler` extension point.

## Subagents

`src/agent/subagents.ts` defines the `Subagent` type and the `SubagentConsumer`. Three paths converge on `invokeSubagent`:

1. `ctx.spawnSubagent(name, payload, options)` — direct, no Stream. Plugin hooks, main-agent `spawn-subagent` tool, plugin commands.
2. Cron with a `subagent` field → `target: { kind: 'new-session' }` → `SubagentConsumer` → `invokeSubagent`. The Stream path exists so the scheduler doesn't need to import the registry.
3. `startSubagent` wraps `invokeSubagent` with a live handle and completion result for sync/background tool spawns. Background completions publish `subagent.completed`; failed runs can carry a captured final message as recoverable output without changing the failed lifecycle status.

Production registry is built from plugin contributions. The bundled memory plugin is auto-loaded and contributes `memory-logger` + `dreaming`. Each plugin `Subagent` may declare `inFlightKey(payload)`; dispatch uses `${parentSessionId}:${name}:${key}` when a trusted parent exists and `${name}:${key}` for parentless scheduler work. `payloadSchema` is validated by the cron loader at parse time and on every `reloadAll()`.

### Background result continuity

For direct channel-background tool launches, the router durably accepts an owed response before the child starts. `src/channels/background-obligations.ts` owns those JSON records; `LiveSubagentRegistry` owns execution status, and transcripts own result content. The completion bridge awaits the result-ready write against an existing obligation before enqueueing a wake. Missing live parents or provider failures do not erase the obligation.

The parent claims exact completion IDs and generations before prompt consumption. Successful final-result fetches attach task coverage as well; running polls do not. Only a router settlement decision closes consumed or fetched coverage: a confirmed terminal reply, recognized formal review, substantive non-terminal `channel_send` to the invoking session's exact origin coordinate, explicit skip or `/stop`. Progress, `more_work_this_turn`, willingness, assistant `stop`, `NO_REPLY`, no-op, failed or off-target sends and unrelated output leave the response owed. Siblings are not implicitly covered.

A completion wake is a stream message, not a delivery, but a durable result-ready completion for the exact deferred obligation can carry the previous turn's coverage into a drain that also coalesces fresh input. A generic wake cannot. Reload moves deferred coverage through the bounded reload handoff to a successor session without a synthetic prompt; the successor claims it before its first real prompt.

After process death, boot transfers unresolved background obligations into the fixed runtime-notice outbox, using idempotent import-before-ownership and receipt-before-source-acknowledgment. Obligations sharing a notice partition (exact target, account, canonical principal and effective captured parent) with older-epoch inbound requests are prepared into one mixed notice before the background-only fallback runs. A confirmed notice ends its exact coverage. The notice does not require a provider, transcript reopen or model follow-up. Healthy settlement produces no extra notice; failed local settlement after a landed reply, review or origin send can produce a conservative notice alongside that answer, never replay of the answer or work.

Inside a running process the router does not wait for a restart. When a parent turn ends, or idle eviction or stale rollover would discard it, with consumed results still owed and no running child or queued retry to carry them, the router transfers them to a live-turn-ended notice in the same outbox; the running dispatcher delivers it. A provider-error notice settles only the failed turn's own inbound requests, never consumed child results. Only real process death or shutdown produces the frozen restart template.

Inbound admission is also durable: `route()` syncs an engaged input before returning an accepted receipt, and the router claims queued IDs before splicing or prompting. A first user message does not depend on the SDK having written its first assistant transcript entry. Mixed inbound/background claims, moves and outcomes are committed to the journal before their idempotent child JSON applications; queues change only after all applications finish. Boot repairs those decisions before notices or background work can dispatch.

Receipt durability is not an upstream transaction. Adapters may acknowledge transport events before routing; unreceived downtime traffic remains subject to platform replay. Instagram advances its local checkpoint only after durable acceptance/duplicate or completed non-engaged classification. Admission identity includes event kind and revision, so synthetic GitHub review rounds remain distinct. Slack is the exception: it admits each message at most once, whatever the revision or routing thread, so any later delivery of an admitted message is a duplicate. An edit that adds a mention can still engage a message that was only observed. GitHub's open-PR catch-up keeps its replay cooldown only for `accepted` or `duplicate` receipts.

Delivery is at least once: remote notice success before a local receipt commit is ambiguous and may duplicate a notice on retry. Unavailable destinations remain blocked and owed until authorized delivery becomes possible. Journal corruption conservatively freezes all potentially mixed background/outbox work; it does not reinterpret surviving child JSON. See [engagement](/docs/internals/engagement#durable-inbound-admission-and-turn-ownership) for admission, storage repair, retention and durability limits.

### Tool-loop termination

`src/agent/loop-guard.ts` combines exact repeated-call detection with a sliding target window. Reads are classified at the awaited SDK `turn_start` boundary: calls for one canonical path emitted in the same assistant tool batch count once. Successful non-empty textual results contribute bounded observed intervals; recorded pages establish the frontier, and exact-adjacent sibling intervals extend it even when parallel calls finish out of order. Suppressed siblings do not count as independent loop observations. Recorded images, overlap, backtracking, gaps, empty results, and malformed ranges retain the coarse path signature and accumulate toward a block.

A confirmed block aborts the active SDK run because returning a tool error alone lets a looping model retry indefinitely. `loop_guard:block` and `loop_guard:deferred_block` are lifecycle failures for subagents; `startSubagent` reports `ok: false` and preserves any assistant result captured before the abort only as recoverable output. Required-result repair retries never convert that forced termination back into success.

## Bundled plugins

`src/bundled-plugins/memory/` ships with TypeClaw and is auto-loaded before user `plugins[]`. Statically imported by `startAgent` and passed via `LoadPluginsOptions.bundled`. Not copied into agent folders, not user-listable. `memory` config block (`{ idleMs, dreaming: { schedule } }`) is restart-required (read once at factory time). **`session.idle` is the prompt-end signal** fired synchronously after every `session.prompt()` in `src/server/index.ts` `drain()`.

## Wire protocol contract

TUI ↔ WS depends on the stream-driven drain loop:

- **Concurrent prompts don't race.** With a Stream wired, `{ type: 'prompt' }` is published to `target: { kind: 'session' }`; per-session drain owns all `session.prompt()` calls. Fallback (no stream) keeps inline behavior for tests.
- **Queued prompts render in execution order.** The TUI doesn't append the `> text` line at submit. Server emits `prompt_started` from the drain loop right after `shift()`. Old containers running pre-`prompt_started` server code leave typed messages invisible — restart after any protocol change.
- **`interrupt`-delivery prompts abort on receipt.** `session.abort()` from the publish path; in-flight `prompt()` resolves immediately; drain dequeues the new prompt.

## Cron split (celery-style)

`src/cron/scheduler.ts` is a pure clock — computes next-fire and invokes `onFire(job)`. Knows nothing about execution. `src/cron/consumer.ts` subscribes, dispatches, and coalesces by jobId. Long-running jobs no longer block scheduler ticks; overlapping fires are dropped by the consumer with a warning.

## `stream_snapshot` agent tool

`src/agent/tools/stream-snapshot.ts` — read-only tool exposing the broker's bounded ring buffer (default 1000 events). Agent can ask "what cron jobs fired in the last minute?" without a round-trip. Wired only when a Stream is injected. Read-only by design.

## Rules of thumb

- **In-memory and ephemeral.** Anything that must survive a restart belongs elsewhere (session JSONL, `cron.json`, MEMORY.md, recovery outbox). Publication alone never settles a durable response obligation.
- **Wire-protocol changes require a container restart.** Source loads once at process start.
- **Each new target kind is a deliberate addition.** Prefer typed targets over a catch-all.
- **Drain loops own serialization.** Broker fans out; doesn't gate.
